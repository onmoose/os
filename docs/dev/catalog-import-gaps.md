# Catalog import gaps

An **append-only ledger** of platform gaps surfaced while importing apps with [`authoring-apps-with-an-agent.md`](authoring-apps-with-an-agent.md). When an app *can* be adapted to a Door-1 catalog app but something didn't fully translate — an env var moose can't inject, a URL it can't supply, an auth secret it can't generate — the import agent records it here instead of losing it in a session transcript.

**This is capture, not the design backlog.** Entries here are raw findings. The curated, prioritized design backlog is [`../specs/NEXT.md`](../specs/NEXT.md); a human triages this ledger and *promotes* recurring or real gaps into NEXT.md (deduped and shaped), then back-references the promotion here. Do **not** write NEXT.md from an import run, and do **not** treat an entry here as a decision — it's a "we hit this, capture it" note.

Unlike `docs/progress/` entries (frozen ADR snapshots), this file is **mutable by design**: append new entries, and edit existing ones to advance their `Status:` (`open` → `planned` → `implemented`, or `won't-do`) as each gap is triaged and eventually resolved.

## How to use it

- **Import agents:** append one entry per distinct gap you hit, using the format below. Newest entries at the bottom. Don't edit NEXT.md.
- **Human reviewer (triage):** after an import, scan new entries (`grep "Status: open"` is the worklist — there's deliberately no standing "go check the ledger" task; the `open` entries *are* the to-do list). If a `gap-class` now recurs across apps, or a single gap is severe (`blocks-start`), promote it to a NEXT.md entry (its own design topic, or fold into an existing one) and the catalog-curation conversation, then move the entry's `Status:` to `planned`. When the mechanism ships, flip it to `implemented` so the next person can grep this ledger for every app that was waiting on that gap and revisit them. **In the same change, add the gap-class to [`capabilities.yml`](capabilities.yml)** (`since:` = brain version, `ref:` = the PR/spec that shipped it) and bump its `version` — that machine-readable entry is what mechanically fires the re-screen of every waiting app (see [`../specs/CAPABILITIES.md`](../specs/CAPABILITIES.md)), rather than relying on someone remembering to grep here. **If the gap-class only closes *partially*** (the shipped mechanism unblocks some apps in the class but not others, or unblocks only one facet of it), don't add the gap-class tag itself — coin a new, narrower id for the shipped facet and add that instead (`../specs/CAPABILITIES.md` # The append-only discipline). Write the mapping into this entry's `Status:` line (name the `capabilities.yml` id it corresponds to) so a reader starting from the gap-class tag can still find it.

**The ledger tracks resolution status; it does not make the decision.** The *design shape* of a `planned`/`implemented` fix lives in NEXT.md and the specs — `Status:` just points there. Keep that boundary: this file says *what gaps exist and where each one stands*; NEXT.md says *what we decided to do about the open ones*.

## Entry format

```
### <gap-class> — <app-id> (<YYYY-MM-DD>)

- **Severity:** cosmetic | degraded | blocks-start
- **Trigger:** the exact env var / directive / assumption that didn't translate
- **What breaks:** one line on the user-visible effect
- **Why moose can't satisfy it (v1):** the missing mechanism
- **Status:** open
```

**Fields:**

- **gap-class** — a short, stable tag so recurrence is greppable. Reuse an existing tag when the gap is the same mechanism (`secret-injection`, `app-url-injection`, …); coin a new one only for a genuinely new mechanism. Same tag across apps is the signal that it's worth promoting.
- **Severity** — the load-bearing field for triage:
  - `cosmetic` — a nicety is off; app fully usable.
  - `degraded` — a real feature is broken (OAuth, email links), but the app runs and core use works.
  - `blocks-start` — the app will not boot until a human sets something the platform should have supplied. This is also a **curation** signal (`NEXT.md` # Store catalog curation policy): a `blocks-start` app may not be shippable as-is.
- **Status** — where the gap stands. New entries start `open`; only a human moves them on (always with the pointer that justifies the move):
  - `open` — the mechanism is still missing. This is the worklist (`grep "Status: open"`).
  - `planned (<NEXT.md anchor / issue #>)` — promoted; the design topic or issue is the link. The shape is decided *there*, not here.
  - `implemented (<spec section / commit / PR>)` — the mechanism shipped. Leave the entry in place — it's now the record of which apps to revisit and re-import against the new mechanism.
  - `won't-do (<reason>)` — **we decided never to build the mechanism.** Not "the app shipped anyway" — see below. The reason (or a `DECISIONS.md` pointer) lives on the line.

  **`Status:` tracks the *mechanism*, not the app.** This trips people up, so state it plainly: an entry stays `open` for as long as moose lacks the mechanism, *no matter what the importing app did about it*. An app that shipped `full` by dropping the feature that needed the gap has not closed the gap — it routed around it, and the next app to need that feature will hit the same wall. The app's side of the story is recorded separately, in the store's `status.yml` (`state:`, and a `by-design` limitation); this ledger's job is to remember that moose still can't do the thing. `won't-do` is reserved for a *platform* decision not to build the mechanism at all — never inferred from an app shipping around it.

  The **Severity** field, not `Status`, is what says how much the app suffered: `cosmetic` already means "app fully usable." A `cosmetic`/`open` entry is a perfectly normal and common state — a real missing mechanism whose absence cost this particular app very little.

### secret-injection — kan (2026-06-05)

- **Severity:** blocks-start
- **Trigger:** `BETTER_AUTH_SECRET` — the Better Auth library requires a 32+ char random secret to sign auth tokens and throws on startup without it.
- **What breaks:** the app will not start until the secret is set in the instance environment.
- **Why moose can't satisfy it (v1):** no per-app secret-generation/injection mechanism exists — there is no `MOOSE_SERVICE_*`-style or manifest field for an app-specific random secret. Affects any app needing a JWT/HMAC signing secret.
- **Status:** implemented (`DECISIONS.md` 2026-06-05; `APP_MANIFEST.md` # D2). Manifest `secrets: [{name}]` → brain generates a CSPRNG value and injects `MOOSE_SECRET_<NAME>`; kan's compose now maps `BETTER_AUTH_SECRET: ${MOOSE_SECRET_AUTH}`. Security hardening tracked open in `NEXT.md` # App-secret injection hardening.

### app-url-injection — kan (2026-06-05)

- **Severity:** degraded
- **Trigger:** `NEXT_PUBLIC_BASE_URL` — Next.js needs its own public URL for auth redirects (OAuth callbacks, password-reset email links).
- **What breaks:** OAuth providers and email links break; credential login (`NEXT_PUBLIC_ALLOW_CREDENTIALS: "true"`) works without it, so basic use is fine. Left empty.
- **Why moose can't satisfy it (v1):** ~~no URL-injection mechanism~~ — **correction:** the brain *does* inject the routed URL as `MOOSE_APP_URL` (`internal/lifecycle` writeEnv; e.g. `http://kan.local`). The original finding was wrong: this is a manifest-mapping fix, not a missing mechanism.
- **Status:** implemented (no platform change needed). kan's compose now maps `NEXT_PUBLIC_BASE_URL: ${MOOSE_APP_URL}`.

### app-url-injection — docuseal (2026-06-05)

- **Severity:** degraded
- **Trigger:** `FORCE_SSL=${HOST}` — DocuSeal uses the `HOST` env var (the app's public domain) to configure its own base URL for generating links in outbound emails (signature requests, completion notifications, document download links).
- **What breaks:** signature-request emails sent to recipients carry wrong or empty URLs if DocuSeal's Rails stack doesn't infer the public host from Caddy's forwarded headers (`X-Forwarded-Host`). Core app UI is fully reachable; the signing workflow via email links may be broken.
- **Why moose can't satisfy it (v1):** ~~same missing mechanism as `kan`~~ ~~**correction:** `MOOSE_APP_URL` is injected by the brain, so this is a manifest-mapping fix~~ — **re-corrected (2026-06-11):** mapping the injected URL does *not* satisfy this gap, for two reasons. (1) `MOOSE_APP_URL` is a full URL with scheme (`http://docuseal.local`, `internal/lifecycle` writeEnv `lifecycle.go`), but DocuSeal's `HOST` expects a bare hostname it concatenates a scheme onto — feeding it the URL double-stamps the scheme into links. There is no bare-host (`MOOSE_APP_HOST`) variant injected. (2) More fundamentally, the injected host is the `.local` mDNS name, which is link-local — it only resolves for a recipient on the same LAN. The DocuSeal email workflow's whole point is sending to an *external* signer, so correct on-LAN links don't fix the headline use. `FORCE_SSL` must also stay unset (moose serves `.local` over HTTP only, `DISCOVERY.md`). The real unblock is the public/remote app URL, not env mapping; when that lands the toggle rewrites `.env` and the container must be recreated to pick it up (env is read only at `compose up`). End-to-end email signing additionally needs the SMTP relay (see `smtp-relay` entries / #122).
- **Status:** open — degraded, gated on public/remote-URL access (and #122 for outbound mail), not a manifest-mapping fix. Compose left as-is (mapping the `.local` URL would falsely imply the workflow works); user-facing limitation noted in `catalog/docuseal/manifest.yml` long description. Revisit when remote access ships.

### oneshot-job-restart — kan (2026-06-05)

- **Severity:** blocks-start
- **Trigger:** `migrate` service with `restart: "no"`, gated by `web`'s `depends_on: {migrate: {condition: service_completed_successfully}}` — the common "run migrations as a one-shot job, then serve" Compose shape.
- **What breaks:** the brain's `compose.override.yml` force-stamps `restart: unless-stopped` onto *every* service (`APP_LIFECYCLE.md` # Locked: override file contents). The migrate job exits 0, Docker restarts it, it never reaches the "completed" terminal state, so `web`'s completion gate never fires and `docker compose up -d` hangs indefinitely — the install transaction wedges (observed: live kan boot hung past a 600s timeout). Surfaced *after* managed-Postgres unblocked kan's database dependency.
- **Why moose can't satisfy it (v1):** the forced-restart rule doesn't distinguish long-running services from one-shot jobs. Fix = honor author-declared terminating policies + completion-gate targets, and bound `compose up -d` so a never-completing gate fails the install instead of hanging.
- **Status:** resolved (#92, 2026-06-05). `writeOverride` now exempts author-declared terminating jobs and completion-gate targets from the forced restart (`main_service` stays always-forced), and `compose up -d` is bounded by the health-wait budget. kan boots end-to-end against managed Postgres (`TestLiveKanBoot` un-skipped + passing). `DECISIONS.md` 2026-06-05, `docs/progress/one-shot-job-restart.md`.

### nonroot-data-ownership — poznote (2026-06-07)

- **Severity:** blocks-start
- **Trigger:** the image does its data writes as a non-root service user — php-fpm's pool is `user = www-data` (`docker/php-fpm/www.conf`) and a reminder worker is `user=www-data` (supervisord) — and its `init.sh` runs `chown -R www-data:www-data /var/www/html/data` (under `set -e`, no `|| true`) to make the data dir writable by that user.
- **What breaks:** the container exits 1 on first boot. `init.sh`'s chown fails (`chown: /var/www/html/data: Operation not permitted`) and `set -e` aborts startup before supervisord runs. And even past that, php-fpm (www-data) cannot create or write the SQLite DB under the data dir, so no notes can be saved. Both confirmed by running `ghcr.io/timothepoznanski/poznote:6` under moose's sandbox (`--cap-drop ALL --security-opt no-new-privileges:true`, root-owned data bind): the init chown fails, and a direct `--user 82:82` write to the root-owned bind returns `Permission denied`.
- **Why moose can't satisfy it (v1):** moose creates the folderless instance data dir (`<instance>/data`) owned by the brain's uid — root in production — at mode `0o755`, and never chowns it (`internal/lifecycle` `writeInstanceDir`; there is no `chown` anywhere in the brain). A folderless Tier-3 app gets no `user:` from the override (`APP_ISOLATION.md` # User content) and runs as the image default under `cap_drop: ALL`. So an app whose writes happen as a non-root user can't write the root-owned dir, and it can't chown the dir itself because `CAP_CHOWN` is stripped. Unlike a single-process app that can just run as root (cf. `runtime-self-patch — jotty`, which escaped this by running `node` as root), Poznote hardcodes www-data across php-fpm and a worker via baked configs; forcing it to root would mean rewriting `www.conf`, adding php-fpm's `-R` flag, and changing the supervisord worker user at container start — config surgery, not adaptation.
- **Status:** planned-partial — moose's answer to the gap-class is `service_user: true`: a folderless app gets a dedicated, moose-allocated non-root identity (stable per instance, from a reserved app-service band) with `data/` chowned to it (#116, `APP_ISOLATION.md` # Runtime identity & data ownership, `DECISIONS.md` 2026-06-10). That unblocks images that *adopt* the runtime `user:`. **poznote specifically is not unblocked by it** — it hardcodes `user = www-data` in php-fpm/supervisord (ignores the runtime `user:`) and its `init.sh` chowns under `set -e` (fails on the stripped `CAP_CHOWN`), so it stays a curation-reject pending user-namespace remap (`NEXT.md` # User-namespace remap for hardcoded-internal-UID app images). Still no `catalog/poznote/` files written. Reported on #90, assigned to onel. **Partial closure:** the shipped mechanism (identity allocation #116 + the every-bind-dir chown generalization #147) is recorded in `capabilities.yml` under id **`service-user`**, not this gap-class's own tag — the gap-class itself stays open pending `userns-remap` (`../specs/CAPABILITIES.md` # The append-only discipline).

### managed-mysql — ghost (2026-06-07)

- **Severity:** blocks-start
- **Trigger:** `database__client: mysql` — Ghost requires MySQL 8 in production. Its SQLite path is dev-mode-only (official image docs: SQLite "is not available in production mode because an external MySQL server is required"), and Ghost has no Postgres support at all, so moose's managed Postgres cannot serve it.
- **What breaks:** Ghost will not boot — there is no database moose can give it. Managed services don't offer MySQL, and a MySQL bundled into the app's own compose fails to initialize (see below). The app was bailed, not adapted; no `catalog/ghost/` files were written.
- **Why moose can't satisfy it (v1):** two compounding gaps. **(1)** Managed services Tier 1 provisions **postgres only** — `internal/manifest` allows `{postgres, redis}` and `internal/lifecycle/services.go` provisions postgres; there is no MySQL/MariaDB type. **(2)** The "ship your own DB, adapted to binds" fallback also fails: `writeOverride` stamps `cap_drop: ALL` + `no-new-privileges` on **every** service in the app compose, and the official `mysql:8`/`mariadb` entrypoints need `CAP_CHOWN` to chown `/var/lib/mysql` and `CAP_SETUID`/`SETGID` (gosu) to drop to the `mysql` user on first init — both dropped, and `cap_add` is rejected by admission. Pinning a fixed `user:` doesn't rescue it either: moose only chowns binds to an elected uid for folder-grant apps (and to the *moose* app uid, not mysql's), and `cap_drop: ALL` also removes `DAC_OVERRIDE`, so a datadir the server doesn't own is unwritable. Net beyond Ghost: **any stateful server image that self-chowns its datadir can't be bundled under the Tier-3 sandbox** — such apps need a managed-service type.
- **Status:** implemented (#108, `SERVICE_PROVISIONING.md` # Catalog (v1), `docs/progress/managed-services-mysql.md`). Managed `mysql` (8.0, 8.4) and `mariadb` (10.11, 11.4) Tier-1 types now provision like Postgres — Ghost is re-importable with `services.database: {type: mysql, version: "8.0"}`.

### managed-mysql — kimai (2026-06-07)

- **Severity:** blocks-start
- **Trigger:** `DATABASE_URL` — Kimai is a Symfony/PHP app that requires an external **MySQL/MariaDB** server. Its entrypoint (`kimai/kimai` `.docker/entrypoint.sh`) parses the URL into host/port/user/pass, defaults the port to **3306**, and blocks indefinitely in `waitForDB()` (`until php /dbtest.php ...; sleep 3`) until a MySQL connection succeeds, then runs `kimai:install` (DB migrations). There is no SQLite production mode. Same gap-class first hit by Ghost (#85).
- **What breaks:** a fresh install never starts — the container loops forever waiting for a DB that doesn't exist, so the install transaction wedges (no main service ever becomes healthy).
- **Why moose can't satisfy it (v1):** moose's managed-database mechanism provisions **Postgres** for apps, not MySQL/MariaDB, and there is no manifest field to request a managed MySQL. The Door-1 model is "apps don't bundle their own database" (managed Postgres exists precisely so they don't), and Kimai speaks only the MySQL dialect, so neither path is available. Bundling a `mariadb`/`mysql` service in the catalog compose would also re-hit `nonroot-data-ownership` (the DB image drops to the `mysql` user, which can't write moose's root-owned instance data dir). Secondary, independent of the DB: Kimai's own entrypoint runs as root and `pwconv`/`grpconv`/setuid-drops the web server to `www-data` (needs the stripped `CAP_SETUID`/`CAP_SETGID`/`CAP_CHOWN`) → `nonroot-data-ownership` again.
- **Status:** implemented (#108, `SERVICE_PROVISIONING.md` # Catalog (v1), `docs/progress/managed-services-mysql.md`). Kimai is re-importable against a managed MySQL/MariaDB (`DATABASE_URL` ← `MOOSE_SERVICE_DATABASE_DSN`); the secondary finding stands on its own — Kimai's entrypoint still runs `pwconv`/setuid-drops to www-data, so re-import must re-check it under the sandbox.

### gpu-local-inference — open-webui (2026-06-07)

- **Severity:** degraded
- **Trigger:** upstream's `docker-compose.yaml` bundles an `ollama` service (`image: ollama/ollama`) so the app can run LLMs *on the box*; that's the headline "self-hosted local LLM" use. Local inference is only practical with a GPU.
- **What breaks:** moose can't pass a GPU through to a container yet (#67, GPU runtime wiring, `blocked`), and CPU-only Ollama is impractical for real models — so the bundled-Ollama mode isn't shippable. The catalog app drops the `ollama` service and ships **frontend-only**: Open WebUI is fully functional, but the user must point it at an *external* model backend (an OpenAI-compatible API over the internet, or an Ollama running on another LAN box) via the in-app Connections settings. No on-device inference.

Without it there's no point bundling Ollama. Note: the frontend itself runs cleanly under the Tier-3 sandbox — the image defaults to root (`ARG UID=0`), so it writes moose's root-owned `./data` with no `nonroot-data-ownership` issue (smoke-tested healthy under `cap_drop: ALL` + `no-new-privileges`), and it fetches its RAG embedding model from HuggingFace on first boot (hence `internet: true`, cached in `./data` thereafter).
- **Status:** open — `catalog/open-webui/` shipped frontend-only (closes #74). The brain GPU slice (#67 — `gpu: true` override + capacity check against the fake host-agent) shipped 2026-06-12, but on-device inference still needs the real `/dev/dri` detection + Intel media stack on hardware (#125, open, blocked on the VM/bare-metal outer loop). Revisit to offer a bundled-Ollama variant once #125 lands and is validated on real Intel iGPU hardware.

### runtime-self-patch — jotty (2026-06-07)

- **Severity:** degraded
- **Trigger:** Jotty's `docker-entrypoint.sh` raises the Server Actions upload limit (`JOTTY_BODY_SIZE_LIMIT`, default `100mb`) at container start by rewriting files inside its own bundled `node_modules` — a "runtime patcher" that exists because Next.js standalone builds ignore `serverActions.bodySizeLimit` in `next.config` (howto/PATCHES.md).
- **What breaks:** the patch can't run under the sandbox, so the max request body size stays at the Next.js framework default (~1mb). Every Server Actions upload path is affected — note/image attachments, drawio diagrams, and avatar uploads (per the patch's own header) — anything larger than ~1mb fails; text notes, checklists, and Markdown — the core of the app — are unaffected. Worse, the failure is silent and late: the app advertises a 10mb client-side cap (`MAX_FILE_SIZE` in `app/_consts/files.ts`), so the UI accepts a 5mb image and only fails mid-upload when the framework rejects the over-limit Server Action body, rather than rejecting the file up front.
- **Why moose can't satisfy it (v1):** two compounding facts of the Tier-3 sandbox, both rooted in `cap_drop: ALL`. (1) The patcher writes under `/app/node_modules`, which the image owns as uid 1000; with all capabilities dropped the container has no `CAP_DAC_OVERRIDE`, so even running as root it cannot modify code it does not own. (2) The image's entrypoint can't even reach the patcher cleanly: it `su-exec`s from root down to `PUID:PGID`, and su-exec's `setgroups()` needs `CAP_SETGID` (stripped) — verified, the container exits `su-exec: setgroups(0): Operation not permitted`. The catalog compose therefore bypasses the entrypoint and runs `node server.js` directly as root (the identity that owns moose's root-created `./data`), which also skips the patcher. The same class affects any image whose entrypoint self-modifies its bundled code at runtime, or whose `su-exec`/`gosu` PUID wrapper chowns + drops privileges — all of it needs capabilities Tier-3 doesn't grant.
- **Status:** open — shipped degraded (`catalog/jotty`). Note the two sandbox conflicts here have **different fates** and only one is even adjacent to moose's roadmap: (1) the `su-exec` privilege-drop (`CAP_SETGID`) is the same class as the deferred `NEXT.md` # User-namespace remap for hardcoded-internal-UID app images — *but* the catalog compose already neutralizes it by bypassing the entrypoint and running `node server.js` as root, so jotty needs nothing from that work. (2) the residual upload-limit degradation is the `node_modules` self-patch, which is a *file-ownership/capability* gap (`CAP_DAC_OVERRIDE` to rewrite code the app doesn't own), **not** a UID-aliasing one — userns-remap wouldn't fix it, and granting `CAP_DAC_OVERRIDE` to let an app edit its own image is exactly what `cap_drop: ALL` exists to prevent. So there is **no moose-side fix on the roadmap**; the only clean unblock is **upstream making `JOTTY_BODY_SIZE_LIMIT` a runtime setting instead of a `node_modules` patch**. Tracked upstream at [fccview/jotty#422](https://github.com/fccview/jotty/issues/422) (open, `accepted`) — but note the upstream "fix" *is* the patch system, which is the very thing that can't run under `cap_drop: ALL`, so jotty's own resolution of #422 does **not** unblock moose. The real unblock is the non-patch fix a thread participant (dmca-glasgow) is attempting; watch #422 and re-import jotty if it lands. A secondary Next.js cap (`middlewareClientMaxBodySize`, ~10 MB) sits behind the Server Actions one even when the patch works. The broader pattern (self-chowning / privilege-dropping / self-patching entrypoints under `cap_drop: ALL`) recurs and is captured here for triage.

### smtp-relay — kimai (2026-06-09)

- **Severity:** degraded
- **Trigger:** `MAILER_URL` — the image defaults it to `null://localhost`, Symfony's discard-everything transport, so all mail is silently dropped until an admin supplies a real SMTP DSN. Second app in this gap-class (see `smtp-relay — ghost`).
- **What breaks:** every email Kimai sends — "forgot password" reset links and any mail an admin enables later (scheduled report delivery, notifications). Silent failure: the UI reports the mail as sent. Workaround inside the app: an admin can reset any user's password from the admin UI, so nobody is permanently locked out. Core time-tracking is unaffected.
- **Why moose can't satisfy it (v1):** same missing mechanism as the ghost entry — moose has no outgoing-mail relay, no `MOOSE_SMTP_*` injection, and no per-app env-override UI through which a user could supply their own provider's credentials post-install.
- **Status:** implemented (#122 — BYO outgoing mail, `SERVICE_PROVISIONING.md` # BYO outgoing mail). `catalog/kimai` declares `mail: {optional: true}` and maps `MAILER_URL: "${MOOSE_MAIL_DSN:-null://null}"` + `MAILER_FROM: "${MOOSE_MAIL_FROM:-kimai@example.com}"`, so a bound instance delivers mail and an unbound one keeps the null transport. Recurred across apps (ghost, gitea, docuseal's email-signing workflow); each needs its own compose mapping.

### smtp-relay — gitea (2026-06-11)

- **Severity:** degraded
- **Trigger:** no `GITEA__mailer__*` env set — Gitea's mailer is disabled by default, so all outbound mail (password resets, registration confirmations, issue/PR notifications, webhook failure alerts) is silently dropped until an admin configures SMTP in the app settings.
- **What breaks:** any email Gitea sends is never delivered. Users can work around a forgotten password via an admin reset from the Gitea admin UI, so nobody is permanently locked out. Core git hosting (repositories, issues, pull requests) is fully functional.
- **Why moose can't satisfy it (v1):** no outgoing-mail relay, no `MOOSE_SMTP_*` injection, and no per-app env-override UI for post-install SMTP credentials. Same missing mechanism as ghost, kimai, and docuseal.
- **Status:** implemented (#122 — BYO outgoing mail, `SERVICE_PROVISIONING.md` # BYO outgoing mail). `catalog/gitea` declares `mail: {optional: true}` and maps the discrete fields onto Gitea's `GITEA__mailer__*` keys — `SMTP_ADDR`/`SMTP_PORT`/`USER`/`PASSWD`/`FROM` from `MOOSE_MAIL_*`, with `GITEA__mailer__ENABLED: "${MOOSE_MAIL_HOST:+true}"` so the mailer is on only when bound (compose's `:+` form is empty/false when the host var is absent; the `USE_TLS`/`USE_SSL` booleans can't gate it since they're always non-empty strings). `PROTOCOL` is left unset — Gitea infers it from the injected `SMTP_PORT` (465→smtps, 587→starttls, 25→insecure).

### nonroot-data-ownership — postiz (2026-06-11)

- **Severity:** blocks-start
- **Trigger:** two images in the required stack write to image-internal, baked-ownership paths at boot. Postiz runs an in-container nginx whose first act is `mkdir /var/lib/nginx/body`; Temporal's `auto-setup` entrypoint hardcodes `dockerize -template /etc/temporal/config/config_template.yaml:/etc/temporal/config/docker.yaml` (destination not configurable; `/etc/temporal/config` is owned by the image's internal `temporal` user, uid 1000; the script runs under `set -eu`). Temporal is not optional: since Postiz v2.12 the orchestrator is a Temporal worker (`libraries/nestjs-libraries/src/temporal/temporal.module.ts` registers unconditionally; docs ship a dedicated migration guide to Temporal), so "drop the Temporal stack" is not an adaptation, it's a different app.
- **What breaks:** the install can never start. Verified live under moose's sandbox in **both** runtime-identity shapes the platform has. As an elected non-root uid (the `service_user: true` / folder-grant shape, tested 2100:2100, `cap_drop: ALL` + `no-new-privileges`): `ghcr.io/gitroomhq/postiz-app:v2.21.8` exits 1 with `[emerg] mkdir() "/var/lib/nginx/body" failed (13: Permission denied)`; `temporalio/auto-setup:1.28.1` exits 1 with `unable to create open /etc/temporal/config/docker.yaml: permission denied`. The old gap-class was retired rather than kept, because no app ever hit it: it described a mechanism that isn't what breaks. Renamed and rewritten below; `onmoose/store#35` tracks the same correction in the store row.

- **Severity:** degraded
- **Trigger:** upstream's optional cron sidecar (a second `nextcloud:apache` container with `entrypoint: /cron.sh`, running `busybox crond`) must **drop privileges to the crontab's account** before executing a job. Its baked crontab is `/var/spool/cron/crontabs/www-data`; crond resolves that *filename* via `getpwnam("www-data")` — which succeeds, since `www-data` (uid 33) is a real baked account — then forks and calls `setgroups()`/`setuid()` to become it. Under `cap_drop: ALL` those calls are denied: `crond: can't set groups: Operation not permitted`, and the job never runs. **The uid moose injects is irrelevant:** verified live under three uids against the stock image — root (0) runs the job; **www-data (33), which is nameable and is the exact account the crontab is keyed to, fails identically**; the arbitrary `service_user` uid (1000) fails identically. `setgroups()` requires `CAP_SETGID` regardless of the target uid, so no choice of uid and no passwd/naming mechanism fixes this.
- **What breaks:** no scheduled background-job runner. Nextcloud falls back to its default **AJAX cron** mode, where maintenance jobs (trash/version expiry, file scans, federation sync, notification dispatch) fire opportunistically on page loads instead of on a fixed schedule. On an instance that sits unvisited — the normal state for a household file server — maintenance simply does not run; upstream explicitly treats AJAX cron as the least-reliable mode and recommends system cron.
- **Why moose can't satisfy it (v1):** `writeOverride` pins `cap_drop: ALL` + `no-new-privileges` on every service with no opt-out, and `CAP_SETGID`/`CAP_SETUID` are exactly the capabilities a privilege-dropping supervisor needs. Granting them back would hand the container the ability to become *any* uid in its namespace — the opposite of what the sandbox is for — so this is a deliberate refusal, not a missing feature. Distinct from `nonroot-data-ownership`: nothing here is a filesystem permission failure on a root-owned path; the process is denied a *capability*, not write access. Recurs for any image whose entrypoint or sidecar drops privileges internally rather than trusting the runtime `user:` — `busybox crond`, `su`/`gosu`/`setpriv` handoffs, supervisors that fork workers under a named account (PHP-FPM pools, nginx `user` directive). The moose-shaped fix is upstream-side: run the workload directly as the injected uid instead of switching to a hardcoded account.
- **Status:** open — shipped in `apps/nextcloud/` (store repo) with no cron sidecar; the AJAX-cron fallback is recorded there as an `ajax-only-background-jobs` limitation (`degraded`), and the app ships `state: degraded` as a result. Not covered by user-namespace remap (`NEXT.md`), which addresses the write-permission class. An app that needs a *scheduled* job under the sandbox needs a platform-side scheduler (a brain-run periodic `exec` into the app container, declared in the manifest) — there is no way for the app's own cron to work.

### nonroot-data-ownership — plunk (2026-07-12)

- **Severity:** blocks-start
- **Trigger:** the image (`ghcr.io/useplunk/plunk`, `Dockerfile` stage 3) `COPY --chown=plunk:nodejs`s its entire tree as **uid 1001**, mode 755, and its entrypoint then **writes four of those baked paths on the boot path**, all under `set -e`: (1) Prisma requires `/app/node_modules/@prisma/engines` to be writable before `prisma migrate deploy` will run at all; (2) `docker/nginx/setup-nginx.sh` `mkdir`s `/etc/nginx/conf.d/` and `cat >`s a fresh `/etc/nginx/nginx.conf`; (3) `docker/replace-urls-optimized.sh` **sed-rewrites the compiled `.next` build output of web/landing/wiki in place**, substituting the real `API_URI`/`DASHBOARD_URI` for the `next-*.useplunk.com` placeholders baked in at build time; (4) it writes a generated `.env` into each of the three standalone Next app dirs.
- **What breaks:** the install never starts. Verified live under moose's exact Tier-3 flags (`cap_drop: ALL` + `no-new-privileges`) in **both** identity shapes the platform can assign — the `service_user`/folder-grant elected uid (tested 2500) and the folderless default of the brain's own euid (tested 0) — and both exit 1 at the *first* step, before the database is touched: `Error: Can't write to /app/node_modules/@prisma/engines`. Root fails identically to the elected uid, because `cap_drop: ALL` strips `CAP_DAC_OVERRIDE`. **Only uid 1001 works**, and at 1001 the app is entirely healthy under the same sandbox (12 migrations applied, all seven PM2 processes online, nginx served the dashboard `200`, zero permission errors in the log) — so this is purely an identity gap, not a sandbox incompatibility.
- **Why moose can't satisfy it (v1):** `writeOverride` pins one moose-owned `user:` on every service (`internal/lifecycle/lifecycle.go`), admission rejects a numeric `user:`, and `service_user: true` allocates from moose's *own* reserved band — the runtime identity is never the image's choice (`APP_ISOLATION.md` # Runtime identity & data ownership), by design, since a manifest-named UID would alias a real host principal under the no-userns-remap model. The **same hardcoded-internal-UID class as poznote / postiz / formbricks**, and plunk is the 4th app of it. **Not rescuable by the postiz tmpfs trick:** postiz's baked writes were pure *scratch* (`/var/lib/nginx`, `/run`, `/var/log/nginx` — pids, logs, body temp), so an empty writable overlay lost nothing. Every one of plunk's four is baked **content that *is* the app** — the Prisma engine binaries, nginx's `mime.types` (the generated `nginx.conf` `include`s it), and the compiled bundles the rewrite exists to patch — so shadowing them with a tmpfs or an empty bind deletes exactly what the write is meant to modify. The URL rewrite is not skippable either: it is the only mechanism by which the dashboard's client JS learns the instance's real API URL. The one residual escape — a one-shot init service that `cp -a`'s several GB of image content into uid-owned binds so the main container can patch the copies — is the "whack-a-mole writable mounts / config surgery" this ledger's `nonroot-data-ownership — postiz` entry already names as forcing, not adaptation.
- **Status:** open — curation-reject, no artifacts written; the verdict is recorded in the store as `apps/plunk/` (`state: blocked`, `listed: false`, `unblock.os_capabilities: [userns-remap]`), which is the durable re-check trigger. Deferred to `NEXT.md` # User-namespace remap for hardcoded-internal-UID app images — the count-trigger there was already met at three apps; plunk makes four and is a clean argument that the class is **not** self-resolving through per-app cleverness (postiz was, formbricks and plunk are not). Worth adding to that item's revisit list on the next human triage pass. Secondary finding, independent of this gap and adaptable when the app is revisited: the API hard-requires the AWS SES env vars (`apps/api/dist/app/constants.js` `validateEnv()` **throws** on a missing `AWS_SES_REGION`, crash-looping `api` + `worker` while nginx/web stay up), so it needs `config:` fields with `required: true` (`operator-env-config`, #264) rather than optional ones.

### conditional-config-requirement — flipt (2026-07-18)

- **Severity:** degraded
- **Trigger:** `config:`'s `required:` is an unconditional boolean (`APP_MANIFEST.md` # D4: "a required field blocks the install button until the user supplies it"). Flipt v1 offers two mutually exclusive browser sign-in methods — GitHub OAuth (`FLIPT_AUTHENTICATION_METHODS_GITHUB_CLIENT_ID` + `_CLIENT_SECRET`) and generic OIDC (`..._OIDC_PROVIDERS_SSO_ISSUER_URL` + `_CLIENT_ID` + `_CLIENT_SECRET`), each gated behind its own `enabled` toggle. The manifest needs to say "these two are required **only when** the GitHub toggle is on, those three **only when** the OIDC toggle is on"; it can only say "required" or "not required", full stop. Distinct from `operator-env-config` (resolved, #264), which was the absence of any operator-config surface at all: the surface exists and works here, and this is a residual facet of its expressiveness — coined separately per this file's partial-closure rule so the two don't get conflated on triage.
- **What breaks:** neither credential set can be marked required, because only one is ever filled and requiring both would make install impossible. So the manifest ships all five fields optional and the toggle/field pairing survives only as prose in the field descriptions and the store description. A user who flips a toggle on and saves without filling that method's fields gets a **non-booting app**: Flipt's config validation rejects an enabled method with an empty `client_id` and exits before serving (`internal/config/authentication.go`, `AuthenticationMethod.validate()`). Recoverable — clearing the toggle from the app's config page restarts it cleanly — but the platform had every fact needed to refuse the bad save and instead let it through to a crash. Recorded on the app side as `apps/flipt/` limitation `auth-toggle-without-credentials` (`degraded`/`open`).
- **Why moose can't satisfy it (v1):** `ConfigField.Required` is a plain `bool` on a flat field list (`internal/manifest/manifest.go`), evaluated per-field with no reference to any other field's value. There is no dependency expression (`required_when: <other field> == true`), no field grouping, and no cross-field validation hook at either of `config:`'s two entry points (the install consent form and the post-install Settings editor), so the brain cannot know that one blank field is fine and another is fatal. The shape isn't Flipt-specific: it recurs for any app offering **alternative** credential sets rather than a flat list of independent optional keys — pick-one-of-N auth providers, pick-one storage backend (S3 keys vs local path vs Azure), pick-one mail transport. Postiz was the easy case that hid this — its provider keys are genuinely independent and individually optional, so a flat list expressed it exactly; a blank key there just leaves one network disabled instead of killing the boot.
- **Status:** open — shipped in `apps/flipt/` (store repo) with all five fields optional and the pairing documented in prose; the app ships `state: degraded` partly for this. Worth noting for triage that the cheap fix may not be `required_when` at all: a `group:` + `one_of` construct (declare the two credential sets as alternatives, brain enforces "exactly one group complete") covers the same apps and reads better on the install form than per-field dependency expressions. Second app in this shape closes the argument either way; one app is not yet a pattern.

### grpc-ingress — laminar (2026-08-14)

- **Severity:** degraded
- **Trigger:** Laminar's `app-server` listens twice — HTTP on `PORT` (8000) and **gRPC on `GRPC_PORT`** (8001) — and its SDKs export OpenTelemetry spans over gRPC **by default**. A manifest names exactly one `main_service` + `main_port`, so only one of the two can be routed.
- **What breaks:** an SDK left on its defaults sends to `<app-host>:8443` and nothing arrives. Verified on a real install: the Python SDK retried against `laminar.local:8443` with `StatusCode.UNAVAILABLE … Domain name not found` and no span reached the app; with `force_http=True` the same run posted to `/v1/traces` and the trace was readable seconds later. The JS SDK is worse — the store issue records it as failing quietly.
- **Why moose can't satisfy it (v1):** one app gets one routed port, and the ingress is an HTTP reverse proxy. Even given a second port, the box's Caddy dials **plain HTTP** upstreams, so h2c (gRPC's cleartext HTTP/2) would not survive the hop; gRPC needs either end-to-end HTTP/2 or a `grpc_pass`-style upstream mode, and neither exists. The app-side proxy pattern this repo uses for multi-listener apps (langfuse, plane, baserow, and laminar itself) solves *path* fan-out on one HTTP origin and cannot help here, because the problem is protocol, not path.
- **Status:** open — shipped `degraded` (`onmoose/store` `apps/laminar/`, limitation `grpc-export-not-routed`), with the HTTP-export workaround named in the app's own store description because an unconfigured SDK fails silently. First app of this gap-class. Expect recurrence: any app whose SDK speaks gRPC to its own backend (OTel collectors and agent frameworks are the likely repeat offenders).

### self-call-to-app-url — laminar (2026-08-14)

- **Severity:** blocks-use (see note) — the app boots, serves, and signs you in, but you cannot open a project
- **Trigger:** `NEXTAUTH_URL` — `frontend/middleware.ts` authorizes every `/project/{id}` page and every `/api/projects/{id}/…` route by `fetch`ing **its own public URL** from inside the container (`${NEXTAUTH_URL}/api/auth`, with a shared-secret bearer). The app is asking to reach itself at the address the *browser* uses.
- **What breaks:** the fetch cannot complete, and the middleware treats any failure as "not authorized" (`if (!res.ok) return false`, plus a `catch` that also returns false). So there is no error anywhere: every project page **redirects to `/sign-in`**. You sign in, see your workspace, click a project, and land back at sign-in. Measured on the first boot: `fetch failed` from inside the container, `307` on `POST /api/projects/<id>/api-keys`. It fails on both profiles for different reasons — on **appliance** the container cannot resolve the box's `.local` mDNS name; on **hosted** the name resolves but the request re-enters through the box's ingress and meets the owner-only forward-auth gate, so the middleware gets a login redirect instead of its answer.
- **Why moose can't satisfy it (v1):** the brain injects `MOOSE_APP_URL` and nothing else about the app's own address (`internal/lifecycle/lifecycle.go` writeEnv) — no in-network equivalent, and no bare-host variant (the same missing `MOOSE_APP_HOST` the `app-url-injection — docuseal` entry names). Nothing resolves the app's public name inside its own compose network: appliance `.local` names are published to the LAN by Avahi, not to container DNS, and on hosted the public name resolves only to the box's ingress, which is exactly the thing that gates the request. `access.public_paths` (#415) can carve the called path out of the gate on hosted, but that turns an internal authorization check into an internet round trip on every page load, and does nothing on appliance.
- **Status:** open — laminar shipped by **routing around it**: `NEXTAUTH_URL` is set to the compose-network address (`http://frontend:5667`) so the self-call is local, and `NEXT_PUBLIC_URL` keeps `${MOOSE_APP_URL}` for the links the UI renders. That works only because next-auth v4 builds its post-sign-in redirect from the request rather than from `NEXTAUTH_URL` (verified: sign-in still returns the public origin). The gap stays open because the workaround is app-specific luck: an app that uses one variable for **both** the browser-facing origin and its own self-call, or that hardcodes the public URL for one, has no such split. The plausible mechanisms are a `MOOSE_APP_INTERNAL_URL` injection (compose-network address of `main_service`) or in-network DNS for the app's own routed name; neither exists. Severity is deliberately recorded as `blocks-use` rather than `blocks-start` — this ledger's severity list predates that state, and "boots fine, cannot be used" is the honest reading (the store's own severity vocabulary added `blocks-use` for exactly this shape).

### privilege-drop-denied — penpot (2026-08-26)

- **Severity:** degraded
- **Trigger:** `penpotapp/frontend` is an nginx image (`nginxinc/nginx-unprivileged` base) whose entrypoint templates four files **in place** at boot — `/etc/nginx/nginx.conf`, `/etc/nginx/overrides/http.d/resolvers.conf`, an mcp locations snippet, and `/var/www/app/js/config.js` — from `envsubst` over templates in `/tmp`. Its Dockerfile does `chown -R 1001:0` + `chmod -R g+w` on `/etc/nginx` and `/var/www`, so those paths are writable by uid **1001** or by anything in **gid 0**, and by nobody else. Neither identity moose can assign lands in that set, and the two fail differently. **As root** (the folderless default, the brain's euid in production) the templating succeeds and then nginx will not start: started as root it *always* drops privileges to its worker user, and both halves of that need capabilities `cap_drop: ALL` removes — `nginx: [emerg] chown("/tmp/client_temp", 101) failed (1: Operation not permitted)`, and with `user root;` forced past the chown, `initgroups(root, 0) failed (1: Operation not permitted)`. **As an arbitrary `service_user` uid** nginx runs fine, but the entrypoint has no `set -e`: it prints `Permission denied` for each of the four files and then `exec`s nginx anyway on the base image's stale baked config. Verified live under moose's exact Tier-3 flags at uid 0, uid 1000 and uid 4242.
- **What breaks:** as root, the app never boots. As an allocated uid it boots and looks healthy while serving the base image's **nginx welcome page** — no backend upstream, no exporter upstream, no DNS resolver line, no `client_max_body_size`. The second is the dangerous one: the container is up, the process is nginx, and only the app's own `/readyz` path tells you anything is wrong.
- **Why moose can't satisfy it (v1):** the same deliberate refusal as `privilege-drop-denied — nextcloud` — `writeOverride` pins `cap_drop: ALL` + `no-new-privileges` on every service with no opt-out, and `CAP_CHOWN`/`CAP_SETGID` are exactly what a privilege-dropping supervisor needs. That entry already predicted this case by name ("supervisors that fork workers under a named account (PHP-FPM pools, **nginx `user` directive**)"); penpot is its second app, which is the recurrence signal this file exists to capture. Note it is a **compound** with the hardcoded-internal-UID class (`nonroot-data-ownership` — poznote / postiz / formbricks / plunk): each identity is blocked by a different mechanism, so fixing either one alone would not be enough. User-namespace remap (`NEXT.md`) addresses the write half but not the capability half; a root container would still be unable to drop privileges.
- **Status:** open — shipped in `apps/penpot/` (store repo, PR #77) with an entrypoint wrapper that makes the image uid-agnostic: it copies `/etc/nginx` and `config.js` into `/tmp`, rewrites the absolute `/etc/nginx` paths inside upstream's own entrypoint script and its config templates to point at the copy, and runs upstream's entrypoint unchanged apart from those paths, with `service_user: true` supplying the uid. That is a per-app route around the gap, not a closure: the next nginx-family image with baked-in privilege drop hits the same wall and needs its own wrapper. Unlike plunk, the wrapper is cheap here because everything written is **config**, not app content, so relocating it loses nothing. Two adjacent findings worth carrying into the process docs rather than this ledger: a Gate-B probe that stops at nginx's first upstream-DNS `emerg` never reaches worker startup and so reports a clean root boot that does not exist (this is what the penpot screen did), and `health_probe`'s default "any status under 500 is healthy" passed the stale-config **404**, so the broken install went green until `healthy_status: [200]` was pinned.

### host-only-admin — pocket-id (2026-08-31)

- **Severity:** degraded
- **Trigger:** upstream's documented way back into an account whose passkey is gone is a command run **inside the container** — `pocket-id one-time-access-token <username>`, which prints a single-use sign-in URL (`backend/internal/cmds/one_time_access_token.go`). Pocket ID is passkey-only, so this is not a nicety, it is the recovery path for the app's only credential.

- **Severity:** degraded
- **Trigger:** the app runs **two** inbound HTTP listeners: the harness server on `OMB_PORT` and a webhook receiver on `OMB_WEBHOOK_PORT`, both bound to `127.0.0.1`. A general fix would be letting a manifest declare more than one routed path-to-service mapping; that does not exist today.

- **Severity:** degraded
- **Trigger:** the app installs its agent CLIs at runtime from its own Settings page, and `serverInstallFor` (`server/engine-install.ts`) only accepts an install descriptor that is a plain `npm install -g <pkg>` one-liner. Six of the thirteen agents (Grok, Kimi, Droid, Cursor, Qwen, Hermes) ship a descriptor that pipes a shell script into bash instead, so the app refuses them with its own message: *"Installing this engine from Settings is not available on this server. This is the class's **third app** (openclaw adapted around it by seeding a config default, pocket-id recorded it, this one loses a menu), which is the recurrence this file is for. Nothing moose builds fixes it cleanly: the honest fix is upstream shipping npm packages for the other six, and a moose-side "run this command in the app" door would hand a user a shell in a sandbox that exists to deny one.

### nonroot-data-ownership — appsmith (2026-09-21)

- **Severity:** degraded
- **Trigger:** Appsmith bundles a second database it uses for one feature only. Alongside the MongoDB that holds the apps, the image carries a PostgreSQL that backs the built-in sample ("mock") datasources. `init_postgres` in `deploy/docker/fs/opt/appsmith/entrypoint.sh` runs `chown -R postgres:postgres "$POSTGRES_DB_PATH" "$TMP/pg-runtime"` and then drives the server entirely through `su postgres -c ...` (`initdb`, `pg_ctl start`, `pg_isready`, `psql`, `pg_ctl stop`). The chown needs `CAP_CHOWN` and the `su` needs `CAP_SETGID`; moose strips both.
- **What breaks:** not the boot, and that is what makes this entry worth writing. Upstream wraps the call in `safe_init_postgres`, which catches a non-zero `init_postgres` and sets `runEmbeddedPostgres=0` so `configure_supervisord` never copies `postgres.conf` into the supervisord config dir. So the app comes up and works. But `create_appsmith_pg_db` gets there the slow way: it starts the server, then loops `until su postgres -c "... pg_isready ..."` with `max_attempts=300` and `sleep 1`, so the entrypoint sits for **300 seconds** printing `su: cannot set groups: Operation not permitted` once a second before it gives up and carries on. Verified at `v2.4.1` under `--cap-drop ALL --security-opt no-new-privileges` against a root-owned bind: still at `Waiting for Postgres to be ready... Attempt 58/300` 90 seconds in. An install left as-is looks hung for five minutes and then silently loses the feature, with the cause buried in a log nobody reads.
- **Why moose can't satisfy it (v1):** the same mechanism as every other entry in this class. A stateful server image that chowns its datadir and drops to its own service account cannot do either under the Tier-3 sandbox: `writeOverride` stamps `cap_drop: ALL` on every service, `cap_add` is refused by admission, and `CAP_DAC_OVERRIDE` goes with the rest so even root cannot write a dir it does not own. `service_user: true` does not rescue it, because the identity Appsmith needs is the image's own baked `postgres` account, not a moose-allocated uid. The shape that *would* fix it is a managed PostgreSQL the app talks to over the network, which moose has: what is missing is any way to tell this app to use it for **only** the mock-datasource database while it keeps its bundled MongoDB for everything else. The two are independent in Appsmith's config (`APPSMITH_DB_URL` versus `APPSMITH_POSTGRES_DB_URL`), so this is plausibly adaptable later; it was not worth a managed service for a sample-data feature on the first import.
- **Status:** open — shipped in `apps/appsmith/` (store repo) as `degraded` with a `mitigated` limitation. The mitigation is one env var: `APPSMITH_ENABLE_EMBEDDED_DB=0` makes the entrypoint skip the whole block, so the boot is clean and the sample datasources fall back to Appsmith's own cloud mock instance instead of a local one. That is a real cost and the store description says so plainly, because it changes the "is my data on the box?" answer for that one feature. Two notes for whoever picks this up. **First, the flag is load-bearing for the runtime identity too:** the non-root bail inside `init_postgres` (`== When running as a non-root user embedded PostgreSQL cannot be used`, then `exit 1`) sits *inside* the block the flag skips, so turning the embedded database off is precisely what lets the app run under `service_user: true` at all. The store manifest documents the two as a pair. **Second, this is the class's seventh app** (poznote, ghost/kimai via `managed-mysql`, postiz, formbricks, nextcloud, plunk, now appsmith) and the first where upstream handles the failure itself rather than dying on it, so the symptom is a long stall and a quietly missing feature rather than a crash-loop. Worth knowing that this class does not always announce itself as `blocks-start`.

### dev-box-nonroot-folderless-identity — rembg (2026-09-22)

- **Severity:** cosmetic
- **Trigger:** a folderless app (no `service_user`, no `folders` grant) runs as "the brain's own euid/gid" (`internal/lifecycle/lifecycle.go:653`, `iso := isolation{uid: os.Geteuid(), gid: os.Getegid(), ...}`). In production that is root (euid 0), confirmed by the surrounding comments at lines 701-775 ("under the production brain (euid 0)"). The store's own remote curation box (`store` `docs/remote-curation-box.md`) runs `os`'s **native** dev brain, which is never root: it runs as the box operator's own unprivileged account. So a folderless app is tested on the curation box under a different, non-root identity than the one it actually ships under.
- **What breaks:** nothing in production, and that is what makes this worth recording rather than adapting around. On the curation box, rembg's container ran as `1001:1002` (the box operator's uid, no `/etc/passwd` entry for it inside the container) and failed twice in a row for reasons that are pure artifacts of that identity, not of the app: first, `pymatting`'s `numba.njit(cache=True)` tried to write a JIT cache next to its own site-packages file (root-owned in the image) and crash-looped under `cap_drop: ALL` without `CAP_DAC_OVERRIDE`; second, with no matching passwd entry, Docker falls back to `HOME=/`, and the app's own `~/.rembg` model-path expansion became the literal path `/.rembg`, unwritable, so every removal 500'd. Probing the same published image directly as literal root (`docker run --cap-drop ALL --security-opt no-new-privileges`, no `--user`) hit neither failure: `HOME` resolved to `/root` from the image's own root passwd entry, and the baked model was found and used without incident. A curator who trusted the box's identity at face value would have wrongly concluded the app needs `service_user: true` or a `HOME`/`NUMBA_CACHE_DIR` workaround in the compose, either of which would ship a value production does not need while hiding that the box, not the app, was wrong.
- **Why moose can't satisfy it (v1):** this is not a moose serving gap so much as a fidelity gap in the curation tooling. The native dev brain is deliberately unprivileged (running it as root on a laptop would be its own hazard), so there is no cheap way to make the box's folderless identity match production's without either running the whole dev stack as root on the curation box specifically, or teaching the dev brain to assume a root identity for folderless apps the way the production brain does.
- **Status:** open. No adaptation shipped in `apps/rembg/` (store repo) for either failure; both are recorded in the app's `notes.md` as curation-box artifacts, with the production-identity claim backed by the direct root probe above rather than assumed. Every folderless app imported against this box before this entry was tested under the same non-root identity; none is known to have hit this specific trap, but nothing before this import checked for it either, so it cannot be ruled out that a past `degraded`/`blocked` verdict for a folderless app was actually this. Worth a note in `store` `docs/remote-curation-box.md` for future importers rather than a mechanism fix, since the fix (root identity, or the box that assumes it) is a bigger design decision than one import justifies.
