# The hosted owner uses sudo over SSH with no password

- **Status:** done
- **Date:** 2026-10-11
- **Specs touched:** docs/specs/DECISIONS.md (new entry 2026-10-11), docs/specs/USERS_AND_GROUPS.md, docs/specs/AUTH.md (# Device access), docs/specs/ENVIRONMENT.md (# Access & files), docs/specs/APP_ISOLATION.md (new invariant), docs/specs/BRAIN_HOST_PROTOCOL.md (# SSH access), docs/specs/BUILD.md (# 1b, the keep list), docs/specs/NEXT.md (# Web terminal in the dashboard), docs/architecture.md

## What was done

Issue #602. It builds on [ssh-screen-on-then-key.md](ssh-screen-on-then-key.md) and the SSH work before it ([ssh-per-account-access.md](ssh-per-account-access.md)). On a hosted box the owner could SSH in with a key but could not use `sudo`: the portal sign-in gives the owner a random password that is thrown away, and `sudo` asked for it. The rescue path that SSH exists for did not work on hosted. Now, while the owner has SSH on, `sudo` does not ask them for a password. `DECISIONS.md` 2026-10-11 records the decision, which changes 2026-05-15 for this one account.

- **Protocol.** `protocol.SetSSHAccessRequest` gains `PasswordlessSudo` (`passwordless_sudo`, `omitempty`, so appliance requests are byte-for-byte unchanged). An older host-agent ignores it.
- **Brain** (`internal/api/ssh.go`). `applySSH` now takes the user id and sets the flag as `enabled && passwordlessSudo(userID)`. `passwordlessSudo` is true only on hosted, only when the id is `box_meta` `sso_owner_user_id`, and only while that account is an admin. It fails closed: a store error reading the owner or the account logs and answers false. The role check is there because the rule names the account, not the `sudo` group: another admin can demote the owner. So `updateUserRole` (`internal/api/users.go`) now holds `sshWrites` from before it reads the target (so a rollback restores the role this request saw) and, after the role change, pushes the owner's SSH again (`resyncOwnerSudo`, which does nothing for any other account, on the appliance, or with SSH off). A demotion removes the rule and a promotion puts it back. If that push fails, the role is put back in the store and on the host, the change is audited as a failure, and the answer is 502, so a member is never left with the rule. Every push goes through `applySSH`, so all callers send the right value without knowing about the flag: Save (`setMySSH`), the delete's revoke (`enabled: false`, so false), and the delete's compensating re-push (`restoreSSH` in `internal/api/users.go`, which sends the owner's flag back). A failed Save does not re-push; host-agent puts its own writes back, and the rule with them (below).
- **host-agent** (`internal/hostagent/sshaccess/sudoers.go`, `sshaccess.go`). A new step in `SetAccess`, after the drop-in and before the daemon step: with `Enabled` and the flag, it writes `/etc/sudoers.d/moose-owner` whole (one line, `<user> ALL=(ALL) NOPASSWD: ALL`, mode `0440`). The candidate is `moose-owner.new` (a dot in the name, so sudo never reads it), checked with `visudo -c -f <candidate>` through the injected runner, then renamed into place. Without the flag, it removes the file only when the file names this account. The file is in the same undo set as the key file and the drop-in: a refused or failed rule puts the key file and the drop-in back, and a failed daemon step (`undo`) puts the rule back too, with mode `0440`. The daemon reconcile in `undo` is not gated on the rule's restore, because sshd never reads it. The name must match `^[a-z_][a-z0-9_-]{0,31}$`, since `ALL` or `%sudo` are valid sudoers syntax that `visudo` would accept. `Manager.SudoersPath` lets tests keep it out of `/etc`.
- **Start reconcile** (`ReconcileSudoAtStart`, called from `cmd/host-agent-real/main.go` right after `buildAgent`, so both the `hosted` and the appliance builds run it). It keeps no state: it removes a leftover candidate, then keeps the rule only if the account it names is enabled in the sshd drop-in (`readDropIn`). A file in a shape moose did not write is removed, including one whose first line is moose's but which holds a second rule. When the drop-in cannot be read, the rule is removed and the error is logged (fail closed). It never writes a rule, since only the brain knows the owner.
- **Keep list.** `sudoers.d/moose-owner` is on `/usr/lib/moose/etc-keep.list`, next to the drop-in it follows. Without it a Debian-major tidy-up would move it to the attic, and the boot lane's upper-layer check would fail on any boot that ends with the owner's SSH on.
- **Fake host-agent** (`cmd/host-agent`): no change. Its set-access handler keeps state in memory and ignores the flag, so `make dev` behaves as before. It builds.
- **No UI change.** No text was added to the SSH screen.

**Preconditions, checked.** `sudo` (and so `visudo`) is in the hosted image: `dev/cloud/mkosi.conf` installs it, `dev/cloud/expected-packages.txt` and `dev/os-lock/cloud-packages.lock` list it, and the boot lane already checks `/usr/bin/sudo` is root `4755` and that `/var/lib/sudo` is a bind mount on the state partition. The owner is created as an admin (`createSSOOwner` and `adoptSSOOwner` in `internal/api/sso.go` call `SetRole(..., RoleAdmin)`), so it is in the `sudo` group. The rule does not need that group, but the second-admin check below does.

**Tests.**

- `internal/hostagent/sshaccess/sudoers_test.go`: the rule is checked with `visudo -c -f <candidate>` before the daemon step, installed `0440` with the one line, and no candidate is left (`TestOwnerRuleIsCheckedThenInstalledReadOnly`); no flag means no file and no `visudo` call, which is every appliance call (`TestNoRuleWithoutTheFlag`); SSH off, or on without the flag, removes it (`TestTurningSSHOffRemovesTheRule`); calls for another account leave it (`TestACallForAnotherAccountKeepsTheRule`); a `visudo` refusal installs nothing, leaves no candidate, removes the new key file, restores the drop-in byte-for-byte and never touches the daemon (`TestVisudoRejectionPutsEverythingBack`); names that are sudoers syntax are refused and their key file rolled back (`TestRuleRefusesANameThatIsSudoersSyntax`); a failed daemon start removes the new rule (`TestFailedDaemonStartRemovesTheNewRule`); a failed daemon stop restores it at `0440` (`TestFailedDaemonStopRestoresTheRule`); the start reconcile keeps a rule for an enabled account and removes one for an account with SSH off, with nobody enabled, in a foreign shape, or with a second rule after moose's line (`TestReconcileSudoAtStart`), removes a leftover candidate (`TestReconcileSudoAtStartRemovesALeftoverCandidate`), and removes the rule when the drop-in cannot be read (`TestReconcileSudoAtStartFailsClosed`). A quick mutation (dropping the restores) failed four of them.
- `internal/hostagent/sshaccess/sshaccess_test.go`: every `Manager` in the existing tests now sets `SudoersPath` to a temp dir, so no test reads the real `/etc/sudoers.d` (it is `0750` on Debian, so a read there would fail for a non-root test run).
- `internal/api/ssh_sudo_test.go`: the hosted owner's enable sends the flag and the disable does not (`TestHostedOwnerGetsPasswordlessSudoWhileSSHIsOn`); a hosted non-owner, and every account on a hosted box with no owner recorded, never gets it (`TestHostedNonOwnerGetsNoSudoFlag`); the appliance never sends it, even for an account the box meta names (`TestApplianceNeverSendsTheSudoFlag`); deleting the owner sends a revoke without it, and the failed delete's re-push sends it back (`TestOwnerDeleteRevokesAndItsRollbackRestoresTheSudoFlag`); demoting the owner pushes their SSH with no flag and promoting them pushes it with the flag (`TestDemotingTheOwnerRemovesTheSudoRule`); a non-owner's role change does not touch SSH (`TestRoleChangeOfANonOwnerDoesNotTouchSSH`); a failed push on demotion puts the admin role back in the store and on the host and audits a failure (`TestFailedSudoPushUndoesTheDemotion`). The harness now records the host role per user (`harness.roles`) for that last check.
- **Boot proof** (`dev/cloud/cloud-assertions.sh`, the `ssh` boot, on the real hosted image): no rule at boot; with the owner's SSH on, the rule is root `440`, holds the one line, `visudo -c` passes, and `ssh owner@127.0.0.1 'sudo -n true'` succeeds; after SSH off the file is gone and `runuser -u owner -- sudo -n true` fails with "a password is required"; a stale rule planted after SSH off is removed by `systemctl restart host-agent.service`; the second test account is now created as an admin, is checked to be in `sudo`, and with SSH on gets "a password is required" from `sudo -n true` over SSH, with no rule on disk.

`make check` is green on this branch. The `CI / Cloud image` run with `-f publish=false -f boots="ssh"` is recorded in the PR.

## Known gaps & deviations

- **#604, a known hole this change makes worse. It should be fixed before or with this one.** A folder source is checked for symlinks only at install; later starts reuse the saved bind path and Docker follows host symlinks. An app that can write `~/Documents` can swap another app's subfolder source for a symlink to `../.ssh`, and when that app is next recreated it can add a key the owner's `Match` block accepts. Before this change that was a shell as the owner; with it, on hosted with the owner's SSH on, it is root. Greptile found it on #603. It is pre-existing `internal/lifecycle` code with its own design question (a check before each start still races Docker's bind), so it is filed as #604 rather than fixed here. `APP_ISOLATION.md`, `USERS_AND_GROUPS.md` and the `DECISIONS.md` entry name it.

- **Boxes that already have the owner's SSH on get the rule at the owner's next SSH Save, not on update.** Nothing pushes SSH state at brain start, and the start reconcile only removes. A Save while SSH is on always pushes, so turning SSH off and on, or any key change, writes the rule. Adding a push at brain start would be a new reconcile path and was left out of this change.
- **The rule needs both release lines.** The brain change is the control plane; the host-agent change is the OS. A new brain against an older host-agent sends a field the old one ignores, so the owner keeps the prompt. An older brain against a new host-agent never sends it, so the rule is removed on the next push. Neither mix is unsafe. `minimumAgentVersion` was not raised.
- **A failed undo can leave the rule until the next host-agent start.** If the daemon step of a first enable fails and putting the rule back fails too, the rule stays on disk while the brain rolls its row back to SSH off. The error says the host could not be put back, as for the other files, and the start reconcile removes the rule at the next start. Nothing removes it before then.
- **The rule is not reported in `GET /v1/ssh/state`.** Drift on it is handled by the start reconcile only, not by the brain's heartbeat.
- **The start reconcile cannot tell whether the named account is still the owner,** only whether it has SSH on. An ownership change with SSH left on keeps the rule until that account's next push, which sends no flag and removes it. On hosted v1 the owner never changes.
- **No Activity record for the owner's `sudo` use.** That is #601.

## Review

- **Sonnet agent:** no Block. Three notes, all fixed: the start reconcile read only the first rule line, so a file with moose's line plus a second rule counted as moose's (now exactly one rule line, and a test for it); a failed undo that also fails to put the rule back leaves it until the next host-agent start (now in the gaps above); the lane's "SSH off" sudo check passed on any failure (it now asserts "a password is required").
- **Greptile:** two P1 security findings. "Demoted owner keeps root" was real and is fixed here (the role check and the re-push on role change, above). "Folder apps can reach root" is real and pre-existing, and is #604 (gaps above). A second Greptile pass found that the demotion rollback restored a role read before the lock, so a failed request could undo another request's successful demotion. Fixed by taking the lock before the read and the last-admin check.
