# Ask the owner before an app update that asks for more access

- **Status:** done
- **Date:** 2026-11-06
- **Specs touched:** `UPDATES.md` (# 4 Auto-apply unless permissions expand, # Who gets prompted and its new # As built (#633), # As built (#631), # 6 The permission-expansion prompt, # Admin visibility into other users' versions), `BRAIN_UI_PROTOCOL.md` (the three endpoints, the new `update` fields, `update_prompt_dismissed`), `LOGGING.md` (`app.update_approve`), `DASHBOARD.md` (# Update prompt, Settings → Installed apps → Updates, Settings → Users), `APP_LIFECYCLE.md` (# update + rollback: the folder binds and the network of step 8), `DECISIONS.md` (2026-11-06, "Keep current version" is a no for that version), `docs/architecture.md`, `docs/dev/web-ui.md`

Closes #633, step 4 of the app-update work in #630. [nightly-app-updates.md](nightly-app-updates.md) (#632) made the box apply the updates it may on its own, at night. An update that asks for more access stayed `needs_approval` and was never applied, with no way to say yes. This adds the owner's yes and no, the prompt, the yes on the app's settings page, and the admin's read-only view. It also makes an allowed update really grant what it shows: before, a new folder was never bound, a wider folder kept its old subfolder, and the internet setting never reached Docker.

## What was done

- **The diff is data** (`internal/lifecycle/updatecheck.go`). `widenedAccess` returns `[]store.AccessWant` (kind, device, folder, mode, change, source, path) instead of sentences. A folder item names the source the update binds: the one the old override binds (`instanceFolderSources`), or for a new folder the install default for the scope. The list is worked out for every new version and stored with every class (`instances.update_wants`), so a `service_major` update that also asks for more says so. A `needs_approval` row with no list (from a brain before #633) is classified again by the next check.
- **The yes is in `classifyUpdate`.** An update that asks for more is `available` when the yes on the row covers it: `widenedAccess(accepted access, new manifest)` is empty (`approvalCovers`). `Manager.Update` already classified again under the instance's lock with the manifest it applies, so the guard stays in one place for a person's Update, the nightly window and the yes. The `needs_approval` sentence is now "This version asks for more access. It waits until its owner allows it" ("until an admin allows it" for a household app).
- **`Manager.ApproveUpdate`.** Under the instance's lock (a try-lock: a running change answers "busy"), it refuses a stopped app, an update that does not wait for a yes, a version that is not the one offered, and a manifest that now asks for something else under the same version (it stores the new list). Otherwise it stores the yes with the new manifest's `permissions` and `access.public_paths` as JSON, and the class becomes `available`. Refusals are `*lifecycle.UpdateRefusal`, a plain sentence. `storeCheck` now also stores nothing when the yes changed since the check read the row, so a check in flight cannot undo a yes.
- **What an allowed update binds** (`internal/lifecycle/update.go`). `mountsFromOverride` keeps every old bind as it is, binds a new folder with the install default (and the manifest's `default` subfolder for `pick-subfolder`), and binds the whole folder for one that widens from `pick-subfolder` to `whole`. Install's folder preparation moved into `prepareFolderSources`, which install and the update both call.
- **The network follows `internet`, both ways.** When the `--internal` flag of `moose-app-<id>` does not match the new version, `remakeAppNetwork` takes Caddy off, removes the network, creates it with the new flag, puts Caddy back and runs `docker compose create --force-recreate`. That last step is needed because a stopped container on a removed network cannot start and compose does not notice (I checked this by hand on Docker 28.1 with compose 2.35). `update.json` records `network_remade` first, and `undoUpdate` makes the network again for the old version's flag after it puts the old files back. Two new `DockerDriver` methods: `NetworkInspect` and `ComposeCreate`. This also fixes the #631 gap in [app-update.md](app-update.md): a narrowing update kept the internet.
- **The store** (`internal/store`). Additive columns with defaults on `instances` (`update_wants`, `update_approved_version`, `update_approved_access`, `update_approved_by`, `update_approved_at`, `update_declined_version`) and on `sessions` (`update_prompt_dismissed`). `ApproveInstanceUpdate` clears a decline; `FinishInstanceUpdate` clears the yes, the decline and the list. `UpdateCheck` gained `Equal` and `IsZero`, since a slice field makes it not comparable.
- **The API** (`internal/api/appupdate.go`). `POST /api/v1/apps/{id}/update/approve` (202, the same job as Update via the new `runUpdateJob`), `POST .../update/decline` (204) and `POST /api/v1/me/update-prompt/dismiss` (204). The yes has its own gate, `approverOK`: the owner of a personal app, an admin for a household app. A member on someone else's personal app gets 404 as for every app control; an admin on another person's personal app gets 403. The yes is audited as `app.update_approve` (success, every 403 and 409, and a failure to store it), with `version`, `new_version` and `wants`; the job is audited as `app.update` as before. The decline is not audited. The app DTO's `update` gained `wants`, `declined` and `can_approve`, which depends on the caller, so `toDTO` now takes the request context. `GET /me` carries `update_prompt_dismissed`. OpenAPI and the TS client are regenerated.
- **The dashboard.** `wantLines` in `installSteps.ts` words each item, reusing `permissionLines` and `folderAccess`; a new `PermissionList.vue` draws the lines (write access red) and the install info box uses it too. `UpdatePrompt.vue`, mounted in `AppShell`, opens once per page load when the session has not closed it, with the apps the caller may allow, that wait for a yes and that were not declined for that version. Allow runs the job and shows "Updating…"; Keep stores a decline; the modal closes when every app is decided; the X, Escape or a click outside call the dismiss endpoint. The app's settings page shows the lines and **Allow & update** (or whose yes it waits for). Settings → Users lists, under each person, their personal apps that wait for their yes, read-only. Activity labels `app.update_approve`.

## Design choices

From the maintainer's brief, written into the specs:

- **The yes covers an access set, not only a version.** A later version that asks for no more than was allowed is not asked again; one that asks for more is.
- **The approver gate is stricter than the update gate** (an admin cannot allow new access to another person's personal app).
- **The prompt list is drawn from `GET /apps`**, not a new read endpoint: the DTO carries `can_approve` and `declined`, the dashboard already loads the list, and the admin's view in Settings → Users is a filter of the same list by owner. One less endpoint and no second source that could disagree with the tile.
- **The lock is let go between the yes and the update.** An update that starts in between is classified again under its own lock, and the yes covers only the access the person allowed, so the worst case is that the nightly window applies the allowed update first and the person's job then says there is no update.

My own, small:

- **`ApproveUpdate` takes the lock only when it is free** and answers "busy" otherwise, so the request does not hang for the minutes an update runs.
- **The 409 for "the app is not running" is the same sentence as Update's** ("Start the app before you update it.").
- **A public path is worded** "Anyone with the link can open <path>, with no sign-in": the install screen has no line for public paths to reuse.

## Departures from the issue

- **"Closing it counts as Keep" and "Keep comes back on the next login"** are not built that way. The spec separates the two (`UPDATES.md` # Who gets prompted): Keep is a no for that version, and closing is a dismissal until the next sign-in. `DECISIONS.md` 2026-11-06 records it.
- **The admin cannot allow a personal app's update**, though `authorizeAppMutation` lets an admin control it: the spec says only the owner may.

## Known gaps

- **No notification for a pending yes.** The owner learns of it from the prompt at sign-in, the tile and the settings page. The notification, Settings → Updates and the rollback button are #634.
- **An update that is both `service_major` and asks for more access** stores its list but stays `service_major`, and cannot be allowed. #635 has to decide whether its database move asks first, then the access, or both at once.
- **`lan` is not enforced anywhere** (no macvlan), so allowing it changes nothing at run time. The spec says so.
- **On a box with no remap, a first folder on an app with none is approvable** (the tier stays `host`), and the update then runs the app as its owner instead of the brain's identity. Every image since #530 has the remap on, so it reaches old boxes and dev machines only.
- **The modal was not tried in a browser against a running brain**; it is checked by the type check and the build only. I did not run `make dev`, because another session was using the main checkout at the same time.
- **The rollback leaves the containers of a service only the new version had** stopped on the old network, as before (#631's gap). They are never started.
