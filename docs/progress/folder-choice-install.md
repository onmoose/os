# Folders the user chooses: manifest, admission and install

- **Status:** done
- **Date:** 2026-11-11
- **Specs touched:** `docs/specs/APP_MANIFEST.md`, `docs/specs/APP_ISOLATION.md`, `docs/specs/STORAGE.md`, `docs/specs/BRAIN_UI_PROTOCOL.md`, `docs/specs/BRAIN_HOST_PROTOCOL.md`, `docs/specs/UPDATES.md`, `docs/specs/APP_LIFECYCLE.md`

Closes #657. Builds the manifest and install half of the folder model that [folder-choice-spec.md](folder-choice-spec.md) specced for #655. The user can now point each folder at any path inside the folder limit at install, skip an optional folder, and add extra folders. The folder chooser that lets them do it from the dashboard is the next issue (#658); until it lands, the dashboard sends what it sent before, and the install uses the suggestion.

## What was done

- **Manifest** (`internal/manifest`). `projects` is the seventh folder name. A folder takes `optional: true`, and `permissions` takes `extra_folders: read | write`. `default` no longer needs `scope: pick-subfolder`, and `scope` is still parsed with no effect (a value other than `whole` or `pick-subfolder` is still a typo and still refused). A folder listed twice is refused, and a `default` with an empty or dot level or a colon is refused. `Permissions.FolderApp()` is true for `folders` or `extra_folders`, and every place that picked the folder-app identity or the host tier from `len(Folders) > 0` uses it now (install, update, `pickTier`, admission's `root_setup`, `image_user` and `service_user` rules).
- **Lint warnings for older brains.** `manifest.OlderBrainWarnings` warns when a manifest uses `projects`, or a `default` without `scope: pick-subfolder`. `Lint` returns them, so `moose manifest lint` and `moose manifest check` print them as warnings that do not fail the check.
- **Store** (`internal/store/madefolders.go`). A new `made_folders` table (`user_id`, `name`, `created_at`, primary key on the first two, removed with the user). `AddMadeFolder` (insert or ignore) and `MadeFolders`. Created with `CREATE TABLE IF NOT EXISTS`, so an older box just gets it.
- **Install** (`POST /api/v1/apps`, `internal/api` `resolveElections`). Each `config.folders` item takes `path`, `new` and `skip`, next to `source` and the old `subfolder` (which still works and now means `<Folder>/<subfolder>` for any folder). `config.extra_folders` is a list of `{source, path, new}`. The brain checks the folder limit: every level is a plain name (no empty level, no dot start, no colon); a personal path starts at a use-case folder, a folder with a `made_folders` row for the owner, or a new folder (`new: true`, not `bin`, not `Shared`); a shared path starts at a shared use-case folder. A skip on a required folder, a path with a subfolder, an extra folder on an app with no `extra_folders`, and the same extra folder twice are each a 422. Every 422 has `location` `config.folders.<folder>` or `config.extra_folders[<i>]`, and its message names the folder ("For the Projects folder, …"). Extra folders are named after the last part of their path, with " 2", " 3" on a clash. The install plan carries `optional` and `extra_folders`.
- **Lifecycle.** `FolderMount` carries the chosen `Path` (relative to the home or the shared tree) instead of `Subfolder`, plus `Extra` (the `/moose/extra/<Name>` name) and `NewFolder`. `SuggestedFolderPath` is the one place the suggestion is worked out, for install and update. Extra folders bind with the `extra_folders` mode, and `MOOSE_FOLDER_EXTRA=/moose/extra` is set when there is at least one. A skipped folder has no bind and no `MOOSE_FOLDER_<NAME>`. After host-agent makes a new top-level folder, the brain writes its row.
- **host-agent `prepare-folder`** (`hostagent.ValidUserFolderPath`, real and fake). The check is now the part of the limit host-agent can see: at least one level, no empty or dot level, first level not `bin`. The real walk (`usermgr.prepareUnder`) checks the dot and `bin` rules again, and still opens every level with `O_NOFOLLOW`.
- **Updates** (`mountsFromOverride`, `widenedAccess`). Every folder the old override binds keeps its bind, so the `pick-subfolder` to `whole` case is gone. A new required folder gets its suggestion; a new optional one is left off. A skipped folder that becomes required is a `folder` item with the change `new`, and the approved update binds its suggestion. A skipped folder that stays optional is not in the list, even if its mode widens. Extra folders are read back from the override and kept while the new version declares `extra_folders`.
- **Tests.** Manifest parse and lint; admission (`root_setup` with only `extra_folders`); store rows; `resolveElections` (paths inside and outside the limit, new folders, skip, extra-folder names, every 422 location); the 422 through `POST /api/v1/apps`; the install plan fields; a lifecycle install with `projects` at a chosen path, a skipped optional folder and two extra folders that clash (the `Done when` of the issue); an extra-folders-only app runs as the owner; two update paths (nothing moves and a new optional folder stays off; a skipped folder that becomes required waits for a yes and binds `Notes/Obsidian`); `widenedAccess` cases; host-agent path checks on both branches.

## Known gaps & deviations

- **"Already taken" is only the names moose knows.** A new top-level folder is refused when it is named `bin`, `Shared` or starts with a dot. The brain cannot see a folder the user made by hand over SSH, so `new: true` on that name gets a row for it, and it can be chosen from then on. `STORAGE.md` says a taken name is refused. The listing op of the chooser (#658) is what lets the brain see the home; the check belongs there. The limit protects the user from an app, and here it is the user who names the folder, so this was judged not to block. **Decision for the maintainer.**
- **`new: true` on a name that is already allowed is accepted,** for a use-case folder or a name with a row. So a retry after a failed install, which sends the same body, does not fail. The spec says a taken name is a 422; the strict reading would break the retry.
- **A shared path may start at any shared use-case folder,** not only the one the app's folder is named after. The spec says "the shared `<Folder>` or a folder inside it, as before"; the chooser's shared listing shows every shared use-case folder, so this reading matches the chooser. Written into `APP_ISOLATION.md`. **Decision for the maintainer.**
- **`MOOSE_FOLDER_EXTRA` is set only when there is at least one extra folder,** like a skipped folder's variable. The spec says the brain sets it, without saying when. With no extra folder, `/moose/extra` does not exist in the container, so a set variable would name a missing folder. Written into `APP_MANIFEST.md`.
- **`extra_folders` from read to write is one want item for the folder `extra`.** The spec does not cover it. Without an item, the extra folders would gain write access in an update with no question. The dashboard words it as "Your Extra folder (can add, change, and delete files)", which is plain but not good; the chooser work (#658, #659) can word it better.
- **A colon in a folder name is refused** in the brain, because the compose bind is `<host>:<container>:<mode>`. Not in the spec before; added to `APP_ISOLATION.md`.
- **The admission half of "warn" is in the lint only.** Admission refuses or passes; it has no warning channel, and the box reads both forms fine. The warning is in `manifest.Lint`, which `moose manifest lint` and `moose manifest check` both run.
- **The dashboard is unchanged.** It still sends `subfolder` for a `pick-subfolder` folder and never sends `skip` or extra folders, so an optional folder is always bound to its suggestion today. That is #658.
- **Not run against a real box.** The host-agent walk is covered by its Linux tests and the fake by its HTTP tests; no cloud-image boot was run for this change.
