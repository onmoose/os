# The brain writes Caddy's config again after a recreate

- **Status:** done
- **Date:** 2026-10-13
- **Specs touched:** `CONTROL_PLANE.md` # Locked: Caddy is moose substrate; `HEALTH.md` # Automatic restart; `TESTING.md` # Hosted cloud variant; `docs/architecture.md`; `docs/dev/hosted-boot-proof.md`

This closes #613, a gap [apps-off-ingress.md](apps-off-ingress.md) (#608) found. Since #608 the brain puts a recreated Caddy back on every app's network within one health tick, but a recreated Caddy also starts from the staged `caddy.json`, with no app route, no dashboard route and no TLS policy, and the brain wrote those only at its own startup. So every app answered `404` until the brain restarted. [caddy-probe-socket.md](caddy-probe-socket.md) (#610) added a probe server that is lost the same way, and [auto-restart-unresponsive.md](auto-restart-unresponsive.md) (#598) acts on what the probe reads, so the fix had to bring both back without a false restart.

## What was done

- **A mark that tells the brain's config from the staged one** (`internal/caddy`). The staged `caddy.json` already has the moose server, its trusted proxies and a catch-all with the brain's own `@id` (`moose-catchall`), so the issue's first idea, "the catch-all is missing", cannot see a recreate. `MarkConfigured` writes the `@id` `moose-configured` on the server's `trusted_proxies` object; `Configured` reads `GET /id/moose-configured` and answers `true` on `200`, `false` on `404`, and an error on anything else. Caddy strips `@id` keys before it reads a config, so the mark changes nothing in how Caddy runs. Every write of the trusted proxies without it removes it (the startup's `EnsureServer`, and `RestoreServer`), so it is only there after the caller marked the config written.
- **`caddy.Client.RestoreServer`** writes the server-wide parts again: the trusted proxies, the probe server when it is on (under the probe lock, and only when its catch-all is missing, so no copy is dropped), and the catch-all (`EnsureCatchAll`, which appends it only when missing). Unlike `EnsureServer` it never resets the route list, because it runs while installs and starts may be writing their own routes.
- **`lifecycle.Manager.RestoreRoutes(ctx, only)`** writes each app's route again: the app route of a running app (the same `buildRouteConfig` the install and the startup pass use) and the splash of a stopped or failed one, each with its probe copy. It takes each app's lock with `tryLockInstance` and reads the row again under it. It does not publish mDNS and runs no compose. It returns the apps it could not write: a held lock, an app being installed or uninstalled, a failed write. An app that is gone drops out. `only` limits a call to those apps; `nil` is every app.
- **`cmd/brain/caddyrestore.go`.** `caddyEdge` holds the hosted TLS policy and the dashboard route, which startup now writes through it too, so the startup and the restore cannot drift apart. `caddyRestorer.check` runs on the health tick, after `EnsureCaddyNetworks` and before the restart-loop and probe checks. It is armed at the end of startup, after the dashboard route and the first `MarkConfigured`. Each tick it reads the mark. With the mark gone it writes, in the startup's order: `RestoreServer`, the TLS policy and `:443`, the dashboard route, every app route, then the mark. A failed server, TLS or dashboard write, or an unreadable app list, stops there with no mark, so the next tick starts again. The owed apps are kept and written on each later tick until none is left. The mark goes on even while some are owed, so a second recreate is still seen and starts over with every app. An unclear answer from Caddy changes nothing.
- **No false restart (#598).** The restore runs before the probe on the same tick, so the probe reads the route a browser gets. An app whose route is not back yet answers the probe socket with the no-route mark, or the dial fails while the probe server is missing, and both are no sample, which clears the issue. So a recreate can only delay an automatic restart, never cause one. A running app always gets its app route, never a splash, so the restore cannot make a healthy app read as down.
- **Checked against a real Caddy** (`caddy:2.11.4` in local Docker, admin on TCP, with a probe server on a socket inside the container): the mark is written and read, a Caddy restart (which, like a recreate, starts from the config file) loses it, `RestoreServer` brings the probe server back with one catch-all and no reset, the route and its copy land, and a later `EnsureServer` removes the mark.
- **Tests.**
  - `internal/caddy/restore_test.go`, against the fake admin from #610, which now keeps the trusted-proxy object and appends on a `POST` to a route list: the mark is there only after `MarkConfigured`, and `EnsureServer`, `RestoreServer` and a recreate remove it; a `500` on the read is an error; after a recreate `RestoreServer` brings the probe server back, keeps a route written in between and keeps the catch-all last, with no route list reset; on a whole Caddy it changes nothing and never writes the whole probe server; a missing catch-all is appended; with the probe off it never touches a probe path; a failed step is returned.
  - `internal/lifecycle/restoreroutes_test.go`: a running app gets the same route config the install wrote, a stopped and a failed app get their splash, no mDNS publish and no Docker call; a locked app is owed and written once free, and that second call writes only it; an installing app is owed until it runs, an uninstalled one drops out; a failed write is owed and written on the next call.
  - `cmd/brain/caddyrestore_test.go`: nothing before startup arms it; one read per tick on a whole Caddy; the order server, edge, routes, mark; owed apps asked for alone on later ticks, with the mark already on; a second loss starts over with every app; an unclear answer does nothing; a failed server, edge, routes or mark step leaves no mark and the next tick does it all again.
- **Cloud lane, `access` boot** (`dev/cloud/cloud-assertions.sh`). Step 6d now notes the brain's and the apps' start times and the count of `app.restart.auto` records, and stops the second `probewho` copy (from #598's step 4f) so a splash is in play. The old 6d-1, which proved that an exposure toggle brings the probe server back, is replaced. The new **6d-1**, after the Caddy recreate and with no brain restart: the brain logs that Caddy lost its config, whoami answers through `:80`, the brain logs that it wrote the config again, the stopped copy shows its splash, `/api/v1/health` answers `200` at the apex (the dashboard route), `:443` is bound with the moose server on `:80` and `:443` and the wildcard in Caddy's automate list, the probe socket reaches whoami and `probewho` and answers the stopped copy with its marked splash, and the brain's start time did not change. After one more tick: whoami and `probewho` were not restarted, neither is flagged `app-unresponsive`, and no `app.restart.auto` record was added. Step 6e (a brain restart after the recreate, the updater's order) stays. The access boot's `VERDICT_TIMEOUT` goes from 3190 to 3390.

## How it maps to the specs

- `CONTROL_PLANE.md` # Locked: Caddy is moose substrate: a new bullet for the mark and the restore; the networks bullet no longer says the routes come back only at brain startup; the probe server, certificate-store and catch-all bullets name the restore.
- `HEALTH.md` # Automatic restart: the restore runs before the probe on the same tick, so a recreate still only delays a restart.
- No decision flipped, so no `DECISIONS.md` entry. host-agent's updater still starts the brain last (`UPDATES.md` # 8); that order is no longer what brings the routes back.

## Known gaps & deviations

- **Up to one tick of `404`s.** The restore runs on the 60s health tick, so after a recreate apps answer the catch-all for up to a minute. Watching Docker events for the recreate would be faster, but the socket proxy grants no `EVENTS`, and the issue asks for one tick.
- **An app that holds its lock for long gets its route late.** A restart or an install health wait can hold an app for minutes; its route is written on the first tick after. An install writes its own route at its end anyway.
- **The mark sits on `trusted_proxies`.** An `@id` needs an object, and that one is small and fixed. Anything that writes the trusted proxies without the brain (a person through the admin socket) removes the mark, and the brain then writes its config again, which is harmless.
- **A startup that could not reach Caddy** used to leave the routes out until the next brain restart. Now the first armed tick sees no mark and writes them. That is a side effect, not a goal of this change, and it is proved only by the unit tests.
- **The lane proves the restore on hosted only.** The appliance takes the same path (no TLS policy, `.local` hosts), but the appliance lane is local-only and was not run.
