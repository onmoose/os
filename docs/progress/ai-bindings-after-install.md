# AI bindings after install, and account changes that reach apps

- **Status:** done
- **Date:** 2026-09-26
- **Specs touched:** docs/specs/INSTALL_SETUP.md, docs/specs/BRAIN_UI_PROTOCOL.md, docs/specs/SERVICE_PROVISIONING.md, docs/specs/DASHBOARD.md, docs/specs/SETTINGS.md, docs/specs/LOGGING.md, docs/specs/DECISIONS.md, docs/specs/NEXT.md

## What was done

The fourth piece of step 4 of the install setup plan (`INSTALL_SETUP.md` # 1, # 5 and # 6), after [ai-slot-filling.md](ai-slot-filling.md), which filled an app's AI slots from the installer's accounts at install. That entry's known gaps were that an installed app still showed raw fields, that a key change did not reach the apps using the account, and that a deleted account left its values in the apps. This piece closes all three. It follows the eight 2026-09-26 decision rows that start "Piece 4 extends the config endpoints" and the `DECISIONS.md` entry of the same day, whose spec edits ship in this change.

**Config endpoints carry bindings** (`internal/api/appconfig.go`, `internal/api/aibindings.go`). `GET /api/v1/apps/{id}/config` adds `ai_bindings` (slot, account id, `mine`, the label only for the caller's own account, provider id, model ids), `needs_setup` and `missing`. `PUT` takes `{fields, ai_bindings}`. `resolvePutWithAI` refuses an unknown or repeated slot, passes the slots with an account to the install resolver (`resolveAIBindings`, not a fork), and treats a slot with an empty `account_id` as a clear. It then builds one partial update: every field of a listed slot gets the value its new binding gives, or is cleared, and the typed fields are added. A non-empty typed value for a field of a listed slot, or of a slot that is bound now and not listed, is the install's 422. The result goes through the existing `resolvePutConfig`, so `required` and the "no worse" `requires` rule see the whole edit, and a swap from one provider to another is one save. The provider data is read only when the request has bindings.

**Brain commits first, in one transaction, resolved at commit time.** The handler resolves the request at once for the 422s. The job then calls `lifecycle.UpdateConfig` with a resolver (`configResolver`). Under the app's lock, lifecycle reads the current values and bindings and calls it back; the resolver reads the account rows then. The values and the bindings of the listed slots are stored in one store transaction (`store.SetInstanceConfigAndAIBindings`: replace the values, delete the listed slots' bindings, insert the new ones), then the override is rewritten and a running app recreated through the existing `recreateRunning` and pending-recreate path. So an account edited in between gives its new key, an account deleted in between fails the job with `config.ai_bindings: no such AI account` and writes nothing, and two saves to the same app no longer overwrite each other's fields, because each partial edit is applied to the values as they are under the lock. `SetConfig` now calls `UpdateConfig` with a fixed change, so its behaviour is unchanged.

**Needs setup.** `setupMissing` lists one plain sentence per gap: `Fill in <title>.` for a `required` field with no value, `Pick at least one LLM provider.` for an unmet group made only of `ai` kinds and slots, and `Fill in at least one of: <titles>.` for any other. The config GET returns the list, and `needs_setup` is on every instance of `GET /api/v1/apps` and on `GET /api/v1/apps/{id}`. An app whose manifest copy cannot be read is not flagged, like the public-paths enrichment next to it.

**AI account edit** (`internal/api/aiaccounts.go`). The save is synchronous and audited as before. A `provider_id` change while any app uses the account is `409 apps use this account, so its provider cannot change. Add a new account for the other provider instead`, audited as a failure. When the key or base URL changed and apps use the account, one job (`ai-account-restamp`) runs `lifecycle.RestampAIAccount` with only the account id and the app ids. Under each app's lock it reads the app's bindings and calls back `accountSlotResolver`, which reads the account row then and resolves the slot with its stored model ids (`resolveSlot`). So two quick edits end on the newer key whichever job runs last. It skips a slot bound to another account by then, keeps the app's other values, rewrites the override and recreates the running apps. The response is the account plus `job_id`. A label change starts no job.

**AI account delete.** Still elevated and audited. The account, its bindings (by cascade) and the values those bindings gave each app are removed in one store transaction (`store.DeleteAIAccountAndValues`), which reads the bindings itself, so only slots still bound to the account lose their values; a slot rebound a moment before keeps them. The fields to clear come from each app's own manifest copy, through a callback that does not touch the store (the store has one connection, held by the transaction). If a bound app's manifest copy cannot be read, the delete is refused: a 500 that names the app, an audited failure and an `slog` line with `instance_id` and `err`, and nothing is deleted. Then one job (`ai-account-delete`) rewrites each app's override from the store and recreates the running ones (`lifecycle.RestampConfig`). The answer is 200 `{job_id}` when apps were affected and 204 with no body otherwise.

**Email gets the same propagation** (`internal/api/mail.go`, `internal/lifecycle/restamp.go`). The "v1 accepts that lag" comment is gone. An edit that changes what `MOOSE_MAIL_*` would hold (`lifecycle.MailEnvChanged` compares the rendered lines, so a label or preset change does not count) starts one job (`mail-provider-restamp`) that re-stamps the bound apps' `.env` with `rewriteEnvMail` and recreates the running ones (`lifecycle.RestampMail`). A delete reads the bound apps first, deletes the account (the bindings cascade), and starts a job (`mail-provider-delete`) that drops the lines and restarts. The mail re-stamp needs only the binding and the `.env`, not the manifest, so a deleted account's credentials always leave the app. The multi-app loop is in lifecycle (`restampEach`): one app failing does not stop the others, each failure is logged with `instance_id`, `name` and `err`, and the job fails with `could not update <names>. The rest were updated`.

**`used_by`.** `GET /api/v1/ai-accounts` and `GET /api/v1/mail-providers` give each account the apps that use it, `[{instance_id, name}]`, each app once, ordered by name (`store.AIAccountUsage`, `store.MailProviderUsage`). The edit answers carry it too. New store query `ListMailBindingsForProvider`.

The two delete routes now declare 200 (with `AccountDeletedDTO`) and 204 in the OpenAPI spec, plus their error codes, because a custom 204 entry stops huma adding its default error response. The OpenAPI spec and `web-ui/src/generated/openapi.ts` are regenerated.

**Fixes from review on #508.** The agent review and Greptile found that values resolved before the app's lock could be written after a newer change: an older account re-stamp job could bring back an old key, a config save could bring back a key edited or deleted in between, and an account delete could wipe the values of a slot just rebound to another account. All three now resolve under the lock at commit time (above). Also from that review: a delete with an unreadable manifest copy is refused instead of leaving the key, the mail re-stamp no longer needs the manifest, a binding whose provider left the data can be repaired, a background refetch keeps unsaved picker choices, and every user-facing message says "LLM provider".

**Second review round on #508.**

- A delete that landed between a re-stamp's read of the account and its write could get the deleted key written back. The write now goes through `store.ApplyAISlotValues`, which checks in its transaction that each slot is still bound to the account and skips it otherwise. A config save checks, in its transaction, that every binding it keeps still exists and that every new binding's account exists (`store.ErrBindingGone`); if not it writes nothing and the job fails with `an LLM provider account this app uses was deleted while saving, so nothing was changed. Check the settings and save again`. The store has one connection, so a check and its write cannot interleave with a delete.
- A delete left the key behind when the app's manifest copy no longer declared the bound slot. Each binding now records the app_env names it fills in a new column, `instance_ai_bindings.envs` (JSON, `''` for older rows, added with `ALTER TABLE ... DEFAULT ''`), written at install, on a config save and on a re-stamp. The delete clears by those names and needs no manifest. An older row falls back to the manifest, and a manifest that cannot be read or lacks the slot refuses the delete.
- A key change failed for every native slot while the provider list was empty (right after a boot, or with the catalog down). The re-stamp now needs no provider data (`restampSlot`): the key, the account's base URL (a native slot's stays blank without one; a compatible slot takes the provider's `openai_base_url` when the data has it, else keeps its value) and the stored model ids. An app fails only when its manifest copy no longer has the slot or the account cannot be read.

Tests: store `TestApplyAISlotValues`, `TestDeleteAIAccountAndValuesRecordedEnvs`, and `TestSetInstanceConfigAndAIBindings` now covers a stale kept binding and a missing account (`ErrBindingGone`). Lifecycle `TestRestampAIAccountDeleteBetweenReadAndWrite` and `TestUpdateConfigDeleteBetweenReadAndWrite` (each resolver deletes the account before returning). API `TestAIAccountKeyChangeWithoutProviderData`, `TestRestampSlotRules`, `TestAIAccountDeleteUsesRecordedFields`, `TestBindingsRecordTheirFields`.

**Third review round on #508.** Greptile found that removing an account's own base URL could leave an app on that URL. This happens for the compatible slot when the provider data cannot be read: the re-stamp kept the app's stored value, which was the URL just removed. The edit now passes the removed URL to the job. When the app still holds it and the data gives no `openai_base_url`, that app fails in the job with `the account no longer has its own address, and the provider's usual address cannot be read right now. Save the account again in a few minutes`, and the other apps still update. `TestRestampSlotRules` covers the failure, a removed URL the app does not hold, and the case where the data replaces it. Only the edit that removes the URL knows it. If that job fails and a second edit (say a key change) runs before the data is back, the second job keeps the old URL.

## Known gaps & deviations

- **Not tried in a browser, and not against a running brain.** Only `vue-tsc` checks the UI. The settings screen pickers, the set-by-hand switch, the LLM providers screen, the renamed Email screen and its redirects, the tile warning and the job notices have not been clicked through. The API tests use stopped apps because the harness has no Docker; the running-app restart is covered only by the lifecycle tests with fake Docker.
- **Choices the rows left open.** `missing` is full sentences. Every user-facing message says "LLM provider", including the install and edit 422s (`pick at least one LLM provider`, `keep at least one LLM provider`) and the account 422s (`unknown LLM provider`, `the list of LLM providers is not loaded yet`). Messages that name an account still say "AI account". A typed value for a field of a slot that is bound now and not listed is a 422, like a listed slot, rather than turning the slot into "set by hand"; the user changes such a slot with the pickers. A clear and a binding for the same slot in one request count as the same slot twice. The AI delete clears the values in the same transaction as the account (the row only says "brain first"). An app whose binding has no recorded fields (bound before the `envs` column) and whose manifest copy cannot be read, or lacks the slot, blocks an AI delete (the user can uninstall it). An app whose manifest copy cannot be read is not flagged as needing setup.
- **The provider cannot be changed from the LLM providers screen at all**, not only while apps use the account. The 409 still guards the API.
- **The job's outcome is not audited.** The account save is audited as before; a per-app failure is logged and shown as the job's error, which names apps, not reasons.
- **A binding whose provider has left the provider data** can be removed from the settings screen, but removing the app's only LLM provider is refused by the "no worse" `requires` rule (`keep at least one LLM provider`), so a native slot with no other fitting provider cannot be cleared while it is the only one. A key change for it still works, because the re-stamp needs no provider data.
- **The apps list costs one manifest read and one config query per app** to compute `needs_setup`. That is fine at home-box scale.
- **The email edit form warns about a restart whenever a password is typed**, since it cannot see the stored one; the brain restarts only when the value really differs.
