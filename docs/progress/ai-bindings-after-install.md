- **Status:** done
- **Date:** 2026-09-26
- **Specs touched:** docs/specs/INSTALL_SETUP.md, docs/specs/BRAIN_UI_PROTOCOL.md, docs/specs/SERVICE_PROVISIONING.md, docs/specs/DASHBOARD.md, docs/specs/SETTINGS.md, docs/specs/LOGGING.md, docs/specs/DECISIONS.md, docs/specs/NEXT.md

## What was done

The fourth piece of step 4 of the install setup plan (`INSTALL_SETUP.md` # 1, # 5 and # 6), after [ai-slot-filling.md](ai-slot-filling.md), which filled an app's AI slots from the installer's accounts at install. That entry's known gaps were that an installed app still showed raw fields, that a key change did not reach the apps using the account, and that a deleted account left its values in the apps. This piece closes all three. It follows the eight 2026-09-26 decision rows that start "Piece 4 extends the config endpoints" and the `DECISIONS.md` entry of the same day, whose spec edits ship in this change.

**Config endpoints carry bindings** (`internal/api/appconfig.go`, `internal/api/aibindings.go`). `GET /api/v1/apps/{id}/config` adds `ai_bindings` (slot, account id, `mine`, the label only for the caller's own account, provider id, model ids), `needs_setup` and `missing`. `PUT` takes `{fields, ai_bindings}`. `resolvePutWithAI` refuses an unknown or repeated slot, passes the slots with an account to the install resolver (`resolveAIBindings`, not a fork), and treats a slot with an empty `account_id` as a clear. It then builds one partial update: every field of a listed slot gets the value its new binding gives, or is cleared, and the typed fields are added. A non-empty typed value for a field of a listed slot, or of a slot that is bound now and not listed, is the install's 422. The result goes through the existing `resolvePutConfig`, so `required` and the "no worse" `requires` rule see the whole edit, and a swap from one provider to another is one save. The provider data is read only when the request has bindings.

**Brain commits first, in one transaction.** `lifecycle.SetConfigAndAIBindings` stores the values and the bindings of the listed slots in one store transaction (`store.SetInstanceConfigAndAIBindings`: replace the values, delete the listed slots' bindings, insert the new ones), then rewrites the override and recreates a running app through the existing `recreateRunning` and pending-recreate path. `SetConfig` now calls it with no slots, so its behaviour is unchanged.

**Needs setup.** `setupMissing` lists one plain sentence per gap: `Fill in <title>.` for a `required` field with no value, `Pick at least one LLM provider.` for an unmet group made only of `ai` kinds and slots, and `Fill in at least one of: <titles>.` for any other. The config GET returns the list, and `needs_setup` is on every instance of `GET /api/v1/apps` and on `GET /api/v1/apps/{id}`. An app whose manifest copy cannot be read is not flagged, like the public-paths enrichment next to it.

**AI account edit** (`internal/api/aiaccounts.go`). The save is synchronous and audited as before. A `provider_id` change while any app uses the account is `409 apps use this account, so its provider cannot change. Add a new account for the other provider instead`, audited as a failure. When the key or base URL changed and apps use the account, one job (`ai-account-restamp`) resolves every binding again with its stored model ids (`resolveAccountSlots`, which calls `resolveSlot`) and hands the new slot values to `lifecycle.RestampAIAccount`. That writes them under each app's lock, skips a slot bound to another account in the meantime, keeps the app's other values, rewrites the override and recreates the running apps. The response is the account plus `job_id`. A label change starts no job.

**AI account delete.** Still elevated and audited. The account, its bindings (by cascade) and the values those bindings gave each app are removed in one store transaction (`store.DeleteAIAccountAndValues`). The fields to clear come from each app's own manifest copy. Then one job (`ai-account-delete`) rewrites each app's override from the store and recreates the running ones (`lifecycle.RestampConfig`). The answer is 200 `{job_id}` when apps were affected and 204 with no body otherwise.

**Email gets the same propagation** (`internal/api/mail.go`, `internal/lifecycle/restamp.go`). The "v1 accepts that lag" comment is gone. An edit that changes what `MOOSE_MAIL_*` would hold (`lifecycle.MailEnvChanged` compares the rendered lines, so a label or preset change does not count) starts one job (`mail-provider-restamp`) that re-stamps the bound apps' `.env` with `rewriteEnvMail` and recreates the running ones (`lifecycle.RestampMail`). A delete reads the bound apps first, deletes the account (the bindings cascade), and starts a job (`mail-provider-delete`) that drops the lines and restarts. The multi-app loop is in lifecycle (`restampEach`): one app failing does not stop the others, each failure is logged with `instance_id`, `name` and `err`, and the job fails with `could not update <names>. The rest were updated`.

**`used_by`.** `GET /api/v1/ai-accounts` and `GET /api/v1/mail-providers` give each account the apps that use it, `[{instance_id, name}]`, each app once, ordered by name (`store.AIAccountUsage`, `store.MailProviderUsage`). The edit answers carry it too. New store query `ListMailBindingsForProvider`.

The two delete routes now declare 200 (with `AccountDeletedDTO`) and 204 in the OpenAPI spec, plus their error codes, because a custom 204 entry stops huma adding its default error response. The OpenAPI spec and `web-ui/src/generated/openapi.ts` are regenerated.

## Known gaps & deviations

- **Not tried in a browser, and not against a running brain.** Only `vue-tsc` checks the UI. The settings screen pickers, the set-by-hand switch, the LLM providers screen, the renamed Email screen and its redirects, the tile warning and the job notices have not been clicked through. The API tests use stopped apps because the harness has no Docker; the running-app restart is covered only by the lifecycle tests with fake Docker.
- **Choices the rows left open.** `missing` is full sentences, and the one for AI groups says "LLM provider" because it is shown as is; the install 422s still say "AI provider". A typed value for a field of a slot that is bound now and not listed is a 422, like a listed slot, rather than turning the slot into "set by hand"; the user changes such a slot with the pickers. A clear and a binding for the same slot in one request count as the same slot twice. The AI delete clears the values in the same transaction as the account (the row only says "brain first"). An app whose manifest copy cannot be read keeps its values on an AI delete (logged), and is not flagged as needing setup.
- **The provider cannot be changed from the LLM providers screen at all**, not only while apps use the account. The 409 still guards the API.
- **The job's outcome is not audited.** The account save is audited as before; a per-app failure is logged and shown as the job's error, which names apps, not reasons.
- **A binding whose provider has left the provider data** has no tile on the settings screen, so the slot shows no chosen provider until the user picks one. An edit of that account's key then fails for a native slot (named in the job error), because the resolver cannot check the protocol without the data.
- **The email edit form warns about a restart whenever a password is typed**, since it cannot see the stored one; the brain restarts only when the value really differs.
